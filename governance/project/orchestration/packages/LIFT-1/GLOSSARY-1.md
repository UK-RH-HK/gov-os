# GLOSSARY-1: the repository glossary as part of memory, the product package (DEC-1096 (5))

For the owner. Drafted 2026-11-07 by a product-spec agent for the CTO (session `ad44f5fe`). Nothing here is applied
and no ticket is filed. The product build waits for E2G's result and the owner's approval, tests first (DEC-1096 (5)).

## 1. What is decided, and what this package asks
- **Decided (DEC-1096):** a glossary of the repository's own words is part of memory. It is built and kept current
  automatically. Agents consult it when a search does not answer. It is tested now (E2G), and this package goes beside
  the test.
- **The prototype** (`~/gov-os-runs/D4B/glossary/`): `build_glossary.py` (623 lines), `lookup.py` (195 lines) and 12
  tests on a planted repository.
  - On E0's clone (`c00d525fd420`): 3,158 entries of 17 kinds and a code map of 2,749 names, about 322k tokens
    together (`out/glossary.md`).
  - **Measured here on integrate's head (2026-11-07, this agent):** 3,177 entries and 2,862 names; the build 11.3 s
    wall and 53 MB peak memory; a lookup 3 ms warm (median of 10, max 9 ms), 183 ms for the first in a process with no
    cache; a top-30 answer about 4,900 characters (about 1,200 tokens).
- **E2G** (`E2G-DECLARATION.md`) tests the glossary in E2's condition: when the reader asks to search again, it sees
  the top 30 lookups and gives its words in the repository's vocabulary. A2 against E2's A2 is judged.
- **This package asks the owner seven things (§9):** where the glossary lives; how agents reach it; curated terms;
  using the prototype in the project's briefs now; the timing; the three marked lines on open tickets; and what
  happens if E2G does not help.

## 2. The decision's wording (final, for the owner)
To replace DEC-1096 (1), (2), (3) and (5) once the owner answers §9. Item (4), the test, and the basis stay. The
numbering is kept, so the brackets in the lines below read the same before and after. The text assumes the

> - (1) **What it is:** the repository's own vocabulary, for searching and for asking. It holds the terms the
>   repository defines, the forms of its ids, its decisions, tickets, capabilities and rules by id and title, its
>   record kinds, commands, error codes, namespaces, roles and skills, and a map of its code's names (modules, classes,
>   functions, constants). Every entry is in the repository's own words, with its source path and line. Agents use it
>   to phrase searches, and questions to other agents or to the owner, in the repository's words.
> - (2) **Built and kept current automatically:** generated by a stage of `gov rebuild` from what the repository

>   refer to it beside the search-again practice.

> - (5) **The build, and every adopted repository:** W2-143 (the glossary) and W2-144 (its `gov links` check), tests

## 3. The spec

### 3.1 What it holds
- **Glossary entries:** `{term, kind, id, says, source}`. `says` is one line of at most 200 characters, the
  repository's own wording. `source` is `path:line`.
- **The kernel's kinds** (any repository with the kernel has them):

  | kind | from | entries here (integrate, 2026-11-07) |
  |---|---|---|
  | id-form | the kernel's id patterns and the id shapes the repository uses | 32 |
  | decision | the register the path map names (`decision_register:`), heading and status | 1,092 |
  | ticket | `.tickets/*.md` front matter: wbs_id, title, status, class, role | 207 |
  | capability, master-rule | `docs/contract/` records' front matter | 276, 6 |
  | namespace | the path map's namespaces, with their policies | 18 |
  | record-kind | the kernel schemas, with the schema's own description | 21 |
  | command | `gov` commands and their options, with their help text | 81 |
  | error-code | the codes the code raises, with their message | 89 |
  | role, skill | the kernel role files and skills | 6, 9 |
  | lesson, adr | `docs/lessons/`, `docs/adr/` | 5, 2 |
  | term | glossary, definitions and "terms used" sections; files named GLOSSARY; the curated file | 177 |

- **This project's extra kinds:** list-row (1,003), package (103) and act (50). In the product these are declared in
  the curated file (§3.6), not built in, so the generator stays the same for any repository.
- **The code map:** `{name, kind, qualname, path, line, doc}` for modules, classes, functions and constants (here
  164, 61, 1,474 and 1,163). `doc` is the first line of the docstring, or the constant's comment.

### 3.2 Where it lives: generated under `.gov-runtime/glossary/` (recommended)
- **Files:** `glossary.jsonl`, `codemap.jsonl` and `record.json` (the head built, a digest, counts by kind, size,
  build time, files not mapped with their reason). Beside the store (`.gov-runtime/store.db`).
- **Why there, not a tracked file:**
  - **It changes with every merge.** Every new decision or ticket adds an entry. A tracked copy would change in
    almost every commit and conflict at every merge across the worktrees.
  - **It is derived state, like the store.** `.gov-runtime/` is ignored by git, rebuilt, never authoritative. The
    integration store's halves each get their own copy, at their own head, for free.
  - **The path map stays simple.** Every tracked path must sit in exactly one namespace. A tracked generated file
    would need a namespace and would then be indexed, which duplicates the records it summarises (§3.5).
  - **Size.** 1.3 MB of JSON lines today, growing with the register.
- **What a tracked file would give:** any agent could Read or Grep it without a command, and its diff would show what
  changed. `gov glossary --kind <kind> --all` gives the first; the record's counts give a rough second.

### 3.3 How it is generated
- **From the repository's own statements only:** the places the path map and the kernel name, never a model, the
  network or the GPU. Python code is read with `ast`, never imported or run.
- **Any repository:**
  - places come from the path map (the register's key, the namespaces) and the kernel's paths;
  - id forms: the kernel's own patterns (`common.schema.json`: `DEC-`, `ADR-`, `L-`, the ticket id; `CAP-`, `MR-`),
    plus every other id shape the lexical index already recognises (`lexical.ID_SHAPE`) with at least 3 distinct ids,
    each with its count, two examples and its first defining line;
  - the code map's names come from the code graph built in the same rebuild, for every language it reads; Python
    adds its docstrings by `ast`. Where the code graph was not built, Python is mapped by `ast` and the rest is named
    "not mapped" with the reason;
  - a kind the repository does not have gives no entries, reported "not applicable", never an error.
- **Exclusions, exactly as the lexical index's:** never opened are `fixtures/evaluation/**`, every path with
  `lexical_policy: not indexed`, and every `evaluation_sets` hidden path. The secrets filter runs on every file read,
  as it does for the lexical stage. So the glossary holds nothing the index does not.
- **Deterministic:** two builds on one commit give byte-identical files and the same digest.
- **What changes from the prototype:** the 32 id families and their defining lines, hard-coded today, become the
  rule above; `src/gov/**` paths become the path map's code namespaces and the code graph; the pickle cache goes (a
  first lookup within 500 ms without it, §3.7); the three project kinds move to the curated file.

### 3.4 How it is refreshed
- **A stage of `gov rebuild`,** after `codeintel` (it reads the code graph), named `glossary` in the watch and in the
  result's `stores`. It runs with or without `--no-embeddings`.
- **After every merge:** the integration store's refresh (`gov rebuild --integration`, W2-116, its hook live since
  re-pin window 4) builds the half not in use with this same rebuild. So the half's glossary is built at the half's
  head, and the switch makes it current. No new hook and no new lock.
- **A failure never fails the rebuild** and never blocks the switch: the stage reports `not_recreated` with its
  reason, like `reverse_edges`. Its glossary then lags the store, and `gov glossary` says so (§3.5).
- **Cost per refresh:** about 11 s of one CPU core on this repository (prototype, measured). No GPU, no embedder.

### 3.5 How agents reach it: `gov glossary <words>` (recommended)
- **The command:** `gov glossary <words> [--k 30] [--kind <kind>] [--all] [--root <dir>] [--json]`, class `read`.
  - It prints the k best entries as `kind | term | says | source`, the prototype's lexical score: id-aware tokens,
    snake_case and CamelCase split, the term weighted above its text. An exact id or code name ranks first; a bare
    number finds its id.
  - `--root` reads another tree's glossary, as `gov retrieve --root` does. A worktree has no store, so its agents
    give the integration store's folder, as they do for `gov retrieve` today (EMG-common, DEC-1087 (3)).
  - If the glossary's head differs from the store's, it answers and names `GLOSSARY_STALE` with both heads. If there
    is none, `GLOSSARY_MISSING` names `gov rebuild`.
  - The folder `src/gov/glossary/` makes the command; `cli/main.py` is not changed.
- **When:** when a bundle does not answer (the search-again practice's list), the agent looks up its words, then runs
  its second search in the repository's words. This is E2G's consultation step, done by the agent.
- **Why not inside `gov retrieve` now:**
  - **Indexed as chunks** (the glossary in the lexical and semantic indexes): about 6,000 one-line entries that
    repeat the titles of records already indexed. They would crowd the top 5 and change the bundle E0 to E5 measured.
  - **A glossary facet in the bundle on a miss:** possible later, but it changes the measured bundle and its budget.
    It comes only with a measure, as a new ticket.
  - **The bundle stays byte-identical** with or without a glossary present (a KPI line, §4).
- **"Retrievable as a memory record" (DEC-1096 (3)):** met by its place in the store's build, its entry in the
  rebuild result, and its own read command. It is not a record kind of the record store.

### 3.6 Curated terms
- **One small tracked file:** `governance/project/glossary-terms.yaml` (namespace `project-overlay`, embedded).
  Its schema: `template/governance/kernel/schemas/glossary-terms.schema.json` (new).
- **`terms:`** each with `term`, `says`, `decision` (a decision id) and optional `aliases` (the words people use for
  it). Kind `term`, marked `curated: true`, ranked as the repository's own terms. A term with no decision id is not
  taken: the build's record names it.
- **`kinds:`** the project's extra kinds, each a glob and one line pattern (its term and its text). This repository
  declares list-row, package and act, so the product gives the prototype's 17 kinds here.
- **What it is for:** words the project uses that no record defines ("the lift", "the 138", "the fresh 80" and the
  like). It is not a second glossary: `OWNER-GLOSSARY.md` and every terms section are read already. It starts with
  the three kinds and at most about 20 terms, written by the orchestrator from the register.
- **`gov links` checks it** (W2-144): a term without its decision id, an id that names nothing, or a decision not in
  force. A notice, never a gate, as every `gov links` finding.

### 3.7 Size and speed bounds
| measure | bound | prototype, integrate 2026-11-07 |
|---|---|---|
| build on this repository's main tree | ≤ 30 s, ≤ 200 MB peak memory | 11.3 s, 53 MB |
| files on disk | ≤ 5 MB | 1.3 MB (2.0 MB more with the pickle, which goes) |
| a lookup, warm | ≤ 50 ms median | 3 ms |
| the first lookup in a process, no cache | ≤ 500 ms | 183 ms |
| a top-30 answer | ≤ 8,000 characters | about 4,900 |

The bounds leave room for the register to double. The CTO measures them once on the main tree, median of five.

### 3.8 What it does not do
- It changes no record and writes nothing outside `.gov-runtime/glossary/`.
- It adds nothing to `gov retrieve`'s bundle, to any brief, or to the session start.
- It is no gate: no close, landing, launch or check reads it.
- It runs no model, makes no network call and uses no GPU.
