## 1. Context

- **The close queue rebuilds before every close (DEC-780). Gate (b) then runs `gov check` with the pinned judge, before the close starts (DEC-868).** A red `gov check` stops the queue, and no close is spent.
- **The secrets-indexing check is a hard-block check.** It scans each derived store as the check's own content: the file's bytes, then its SQLite rows as text, then, because the bytes hold zero bytes, the same content with its zero bytes removed. All three go to `gitleaks stdin` in one input, once per rule set (`src/gov/secrets/__init__.py`, `_store_content` and `_holds_secret`).
- **Row W2-M395 (2026-10-20) recorded a different false positive of the same check:** bytes of different fields joined into one token-shaped string. Its fix is W2-45's per-value scan.
- **The standing rule for this case:** "If a queue rebuild hits it, gate (b) stops the queue: bring a P1 package; never rebuild-until-green."

## 2. What happened, with the evidence

- **Timeline (queue log `log/close-queue-20261022-1335/queue.txt`):**

  Nothing was closed and no close run was spent. W2-62's checkpoint commit `2b20aa27` stays.
- **The finding, located.** I printed positions, byte classes and exit codes only, never the matched bytes.
  - The check's input is 403,509,475 bytes. One rule set finds one hit: rule `gov-token-lower`, 62 bytes long, in the check's zero-stripped copy.
  - The same 62 bytes are also in the store's raw bytes, with no zero byte inside them and none just before them, and in no tracked file.
  - **They sit inside a word:** an 84-character identifier, whose first 22 characters are lower-case letters and underscores. The rule begins with a word boundary (`\b(?:sk|pk|rk|tok)[_-]…`), so it cannot match there in the text as written.
- **The cause, shown on the line that holds it** (15,268 bytes):
  - gitleaks over the whole line finds nothing (exit 0);
  - gitleaks over the same line cut at the match's first byte flags it (exit 3);
  - the rule's own expression, with its word boundary, finds no match in the line;
  - without the word boundary it finds three candidates, all inside words.
  So the hit appears only when one of gitleaks' reads of its input begins at that byte, inside the word. Where its reads begin depends on the total size and layout of the input, which every rebuild changes. That is why the halves of the input are each clean while the whole is red, and why my earlier scans of the raw bytes alone, the rows alone and the zero-stripped raw bytes alone were all clean.
- **What I infer, not yet confirmed:** that the reads begin where they do because of how gitleaks splits standard input into pieces. The cut test above shows the effect directly; the test of the fix (option a) settles the mechanism.
- **No secret is stored:** the flagged bytes are part of an identifier, and the rule's word boundary rules them out.
- Scripts (scratch, positions and exit codes only): `rc_probe.py`, `line_of.py`, `chunk_edge.py`, `source_of.py`.

## 3. Why it matters

- **The check can stop any close by chance.** W2-54's on 2026-10-20 and W2-62's today make two of about sixteen queue rebuilds. Each such stop costs a queue run (about 15 to 20 minutes of rebuild and gates) and holds the close it was for.
- **It fails closed, so it is never a hole.** But Wave 2's first exit criterion needs clean `gov close` runs, and a check that turns red at random undermines them, along with the owner's trust in red results.
- **The check must not be weakened.** The fix has to keep every real token at a real word boundary a finding, at any offset in any store.
- **The closes are judged by the pin (`fecb870c`).** A fix on `w2/integrate` reaches a close only with a re-pin. The next re-pin is the first one, after W2-66 and W2-07 (DEC-896).
