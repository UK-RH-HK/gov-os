# P-W2-L423-A — A full commit hash beside one vendor's keyword can stop a close at the secrets-indexing gate (P2)

From: the W2 orchestrator, 2026-10-24, at the owner's request before the first re-pin (row W2-L423). Gates: no close is stopped today; after the re-pin, any close whose `.gov-runtime/` holds the trigger. Classification: Ordinary work: yes, because records and logs quote commit hashes all the time. Consequence: fails closed (a close is refused; nothing is let through).

## 1. Context

- **The secrets-indexing check is hard-block** and walks the whole of `.gov-runtime/`, scratch records and lead logs included (`src/gov/secrets/__init__.py`, `stores_with_secrets`).
- **The check strips every allowlist on purpose.** It drops the `.gitleaks.toml` allowlists and each rule's allowlist (DEC-298), and runs the file's own rules a second time so the defaults' allowlist cannot shelter them (DEC-347). **So an allowlist pattern written in `.gitleaks.toml` would have no effect on this check.** An exemption has to be written in the check's code, as a ticket.
- **The trigger is one of gitleaks' default rules:** a code-search vendor's legacy access token. That token is a bare 40-hex string, the same form as a full git commit hash. The rule fires only when one of its two keywords (the vendor's name, or its token prefix) appears in the same text. This package does not write either keyword, so that it never becomes a trigger itself.

## 2. What happened

**The probe.** I ran the check's own scan function on short synthetic texts, using a real commit id of this repo and no secret (`/tmp/claude-1000/-home-usain-Dynamic-Agentic-Engineering-OS/ced0eb43-d826-42fa-8eab-3ba5655f1a1f/scratchpad/l423_probe.py`, which prints verdicts only):

| Text | Flagged |
|---|---|
| full 40-hex hash, no keyword | no |
| full hash beside the vendor's name | **yes** |
| full hash beside the token prefix | **yes** |
| 12-digit hash beside the vendor's name | no |
| full hash beside the word "token" | no |

**Where it happened.** W2-69's run 2 hit this on three of its own review logs. Their byte-exact copies, kept as evidence in `/tmp/gov-os-lead-W2-69/records-original/`, give 9 hits from this rule. They are also why the record sync cannot hold those copies.

**Today.** No file under the main tree's `.gov-runtime/scratch/`, the orchestration record or the probe folder holds either keyword, so no close is at risk now.

## 3. Why it matters

The keyword is rare; full hashes are everywhere. So the trigger only appears when someone writes about this rule, for example a reviewer quoting gitleaks' rule id while also quoting full hashes. When it does, gate (b) is red, the queue refuses the close, and the close costs a proven re-run (DEC-897 (b)), the way W2-62's chance red did.
