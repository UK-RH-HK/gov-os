# P-W2-49 — The secrets-indexing check times out on today's stores, so every close would be refused (P1; blocks all closes, not the leads)

**From:** the W2 orchestrator (W2-00, DAEO-sdxk), 2026-10-19. **Blocks:** every `gov close` (keystone 2's queue), so exit criterion 1; not the leads (DEC-850 item 2).

## 1. Context
`gov close` runs every declared check (`run_checks`, `src/gov/close/command.py:1052`), and a hard-block check that is RED refuses the close. `secrets-indexing` (CAP-38.b, W1-15) is hard-block: it scans every file under `.gov-runtime/` for a secret. For each file it pipes the bytes, and for a SQLite file its rows as text too, through `gitleaks stdin`, once per rule set (two when the repository's rules extend the defaults), with a 60-second limit per run (`_TIMEOUT_S`, `src/gov/secrets/__init__.py:30`), about 24 files at a time (`ThreadPoolExecutor()` on 20 cores). A run that hits the limit raises: the check fails closed. W1-15 measured it on 2,575 files and 244 MiB in all.

## 2. What happened
- `gov check` under the pin, 2026-10-19 22:00 (`log/pin-check-2026-10-19.json`): 21 GREEN, 2 YELLOW, **secrets-indexing RED**, exit code 1.
- The rerun of the check alone (`log/pin-secrets-rerun.err`): `subprocess.TimeoutExpired: Command '['gitleaks', 'stdin', …]' timed out after 60 seconds`.
- Today `.gov-runtime/` holds 509 MB, of which `store.db` is 250 MB (after the rebuild that indexed the assessment) and the code graph's `codeintel/home/code.db` is 210 MB.
- One pass of gitleaks over `store.db`'s bytes, alone on a quiet machine, takes 11.7 s. The check makes up to four such passes per file while about 23 others share the cores. It is not load from elsewhere: the rerun ran with nothing else running.
- The same check was GREEN in the sweep of 10-18 (`log/sweep-check.json`), when the stores were smaller.

## 3. Why it matters
The close queue (keystone 2) cannot move: W2-53's and W2-54's closes, and every later one, would be refused at the checks, and a refused close may not simply be retried (DEC-780: the ratchet does not retry). The rebuild's 21 minutes (against 2.5 to 3.5 in Wave 1) come from the same per-file gitleaks scan on the indexing side.

Ordinary work: yes, because the stores grow with the indexed corpus in ordinary work. Consequence: other (fails closed: every close and `gov check` refused; nothing fails open, no work is lost). It breaks exit criterion 1, so it comes as a package before any round (w2 prompt §13).

Each keeps the check whole: every file still scanned with every rule set, and a scan that cannot finish still fails closed. Today the declared checks run the tree's `src` (W2-59's gap), so a fix merged into `w2/integrate` reaches the next close at once; after W2-59, it must be in the release the owner re-pins.
- **(a) It rides in W2-50's resume** (DEC-802: a resume that happens anyway). W2-50's branch already rewrites `stores_with_secrets` in the same file (its links into `~/gov-os-runs`), so the fix sits in a function W2-50 owns. The fix: the time limit grows with the content's size (or a large store is scanned in bounded chunks, each with the limit), and the pool is bounded so that large files are not starved. A test designer adds the large-store case; one probe covers both. Cost: about half a day on W2-50's resume; closes resume when W2-50 merges, about day 1 to 1.5. Risk: a second concern in a FULL guard ticket; its probe sees both. Changes: W2-50's card gains one KPI.
- **(b) A new small ticket, W2-63** (STANDARD, engineer; `src/gov/secrets/__init__.py`, the scan only; `tests/unit/secrets/**`), started after W2-50 merges, or stacked on it once W2-50's resume has verified (DEC-786). Cost: about 1 day after W2-50; closes resume about day 2 to 2.5. Risk: low; a cleaner record. Changes: a new card and ticket file.
- **(c) Wait for W2-45** (`gov check` runner semantics and scale). Cost: W2-45 sits behind W2-08 (keystone 8), so no close for about two weeks. Not viable.

## 5. Recommendation
