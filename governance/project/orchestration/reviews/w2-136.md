## Findings

### F1: overlap order ignores which ticket is already running, and nothing enforces it at launch
- **What happens:**
  - `WRITES_OVERLAP` puts two overlapping tickets in series by the fixed key (priority, WBS order, id), with no
    regard to status.
  - On this repository, **10 in-progress tickets are planned to wait for an open ticket** they overlap. For example,
    DAEO-p3ln (in progress) is in batch 11, after open DAEO-wnnz in batch 6, on `src/gov/launch/launcher.py`.
  - `check_lead` admits any ticket named anywhere in the ready list and checks only `depends_on`, `needs` and
    `waits_on`. So DAEO-wnnz's lead would start while DAEO-p3ln is still writing the same file.
  - The dispatcher starts "the first ready.txt entry passing every check" and never reads the `# batch k` headers.
    So the overlap order is enforced by nobody.
  - With `--tickets`, an in-progress ticket outside the selection is not compared at all.
- **Against the KPIs:** the code matches them as written. S4 names the tie key without status. S9 limits the
  launch waits to `depends_on`, `needs` and `waits_on`. The failure line ("in the same batch") is not met.
- **Suggestion:** the CTO decides between two fixes, or a row:
  - order unfinished in-progress tickets before open ones in `key`;
  - or count an overlap with an in-progress ticket as a wait in `check_lead`.
- **Scope:** in (S2, S4, S9). Not blocking.
- Ordinary work: yes, because the plan is run while tickets are in flight (DEC-1088 (6)), and this repository shows 10 such pairs today.
- Consequence: other (two worktrees edit one file in parallel; the conflict shows at integration and is resolved there; nothing is lost and the guard is unchanged).

### F2: the launch check reads the tickets and the ready list of the folder it runs in, not the current ones
- **What happens:**
  - `check_lead(root, …)` calls `load(root)` and reads `READY_REL` under `root`.
  - A lead is started in its ticket's worktree, as `launch_now.sh` `cd`s into it, so the check reads that branch's
    copy of `.tickets/`.
  - That copy drifts in ordinary work. This worktree already lacks two integrate changes to `.tickets/`: DAEO-t8mp,
    W2-136's own dependency, gained a KPI line; DAEO-qskx was added.
- **Two outcomes:**
  - Mostly it refuses: a dependency closed on integrate still reads as open in the worktree.
  - It admits wrongly in one case: a wait added on integrate after the worktree's last merge. That case is ordinary
    while every old ticket gains its `needs:` (W2-128). A worktree's copy without `needs:` plans only on writes and
    `depends_on`.
- **Precedent:** the launcher already reads the main repository for the store (`gov.launch.store.main_root`,
  review F4, "a worktree branched before the line was added still gets it").
- **Scope:** out, because the risk is feature-gated (DEC-803). No lead is started through `gov launch` until W2-20's
  lead line wires it; today the dispatcher calls the CLI directly.
- **Recommendation:** make it an **entry criterion of W2-20's lead line**, which lands with this ticket. The code
  that would change is `plan_check.check_lead`, inside this ticket's paths, so it can ride along if the ticket
  resumes (DEC-802).
- Ordinary work: yes, because leads run in their worktrees and open tickets change in flight; the drift is visible on this branch now.
- Consequence: fails open (only once W2-20 routes leads through `gov launch`; until then nothing calls it).

### F3: the default ready-list path names no file the dispatcher keeps
- **What happens:**
  - `READY_REL = governance/project/orchestration/ready.txt` is read relative to the launch root.
  - The dispatcher's approved list is `<main repo>/.gov-runtime/scratch/orchestrator/dispatch/ready.txt`
    (`dispatcher.py`, `STATE`).
  - Without `GOV_PLAN_READY`, every lead is refused: "no approved ready list can be read".
- **Notes:**
  - `GOV_PLAN_READY` is read from the caller's environment, the one environment read left on the lead path. A stale
    value would point the check at the wrong list.
  - The evidence's first pass already names the location as unstated by the KPI.
- **Scope:** in (S9). Not blocking. W2-20's wiring should set the path, or `READY_REL` should name the dispatcher's file.
- Ordinary work: yes, because any lead launched without the variable set hits it.
- Consequence: other (it fails closed: a lead is refused, nothing starts).

### F4: an override is "logged" only as a stderr line
- **What happens:**
  - `_admit_lead` writes `gov launch: OVERRIDE <DEC-id>: …` through `_say`, which is designed to drop the line
    silently when stderr is closed or unread.
  - S9 says "written in the launch log". `gov launch` has no log file of its own.
  - The override stays recorded on the ticket (`plan_override`) and in the plan's `OVERRIDE` line.
- **Scope:** in (S9). Not blocking.
- Ordinary work: yes, because a caller that keeps only stdout (as `launch_now.sh` does for its session) loses the line.
- Consequence: other (the override's decision id stays on the committed ticket; only the launch-time trace is lost).

### F5: stale text about the lead path
- **What happens:**
  - The evidence's "The change" section still says a lead is "a call from a session whose `GOV_ROLE` is
    `orchestrator` with a `GOV_TICKET` (its own ticket is checked)". The second pass removed that.
  - `gov launch`'s `HELP` ("start a sandboxed worker session") and its `<role>` help list only worker roles.
  - The repository-settings refusals say "a worker session" for a lead too.
  - `command.py` is outside the ticket's paths, so the help text is a row.
- **Scope:** in (documentation of S9). Not blocking.
- Ordinary work: yes, because a reader of the evidence would believe the caller's environment still matters.
- Consequence: other (wording only).

### F6: a `depends_on` that names no ticket is treated as met
- **What happens:**
  - `hard_waits` skips a `depends_on` entry it cannot resolve, and no finding is raised.
  - S5's `UNKNOWN_WAIT` covers only `waits_on`.
  - Both the plan and `check_lead` would admit the ticket.
- **Scope:** out (S5 names only `waits_on`). A Wave 3 row.
- Ordinary work: no, because `gov check graph` already flags `DANGLING_REFERENCE` for a dangling `depends_on`, so a typo is caught at filing.
- Consequence: fails open.

### F7: the lead path does not check who calls it
- **What happens:**
  - Before this branch, `gov launch orchestrator <t>` was refused as "not a worker role".
  - Now any session that can run `gov launch` can start an orchestrator-role lead, with no sandbox, for a ticket that
    is in the ready list with its waits met. That includes an engineer.
  - The guard does not restrict `gov launch` by role.
  - The CTO's settlement (1) deliberately reads no caller environment. The dispatcher's line checks no caller either.
- **Scope:** out (settled by the CTO; S9 does not ask for it). A Wave 3 hardening row.
- Ordinary work: no, because an honest engineer never launches a lead; it needs a deliberate act outside its role.
- Consequence: fails open.
