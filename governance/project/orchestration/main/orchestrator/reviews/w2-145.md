### Findings

**F1: with the pool on, a search the service cannot answer asks it twice and logs twice.** (S4, also P-1)
- `governance/project/retrieval.yaml:12` sets `rerank_depth: 40`. In `retrieve.py:477`, the pool's `rerank()` comes back unscored, so `pool_failed` is set and `pooled` stays None. Then `retrieve.py:576` calls `rerank(query, candidates, None)` again, which runs `default_reranker` → `_ask` a second time.
- Each `gov retrieve` therefore writes two FALLBACK lines. S4 asks for one line per search, so that `gov status` counts as before.
- It also waits twice:
  - No answer within the time limit: about 2 × 30 s.
  - Start refused: the second attempt finds the lock free and starts a second service, with a second REFUSED line. When the refusal is "no GPU slot", that is a second 20 s wait, which P-1 forbids.
- Before this ticket, the private usually scored the pool, so the second attempt did not happen in ordinary work. This ticket makes it the normal path.
- Untested: the W2-145 bundle cases' project has no `retrieval.yaml`.
- Fix inside `allowed_paths`: in `rerank.py`, remember the service's failure for this process for a short window and return unranked with the same reason at once, with no second line. Or the CTO adds `retrieve.py` to the paths so the per-page path does not ask again after a pool outcome of `unavailable`.
- `scope: in`
- Ordinary work: yes, because every first `gov retrieve` in this project hits it whenever the service is unreachable.
- Consequence: other. The search still comes back unranked and named. The harm is delay, the double count in `gov status`, and doubled load on an overloaded service.

**F2: a search that arrives while the service is ending at idle goes unranked, and may give a stale reason.** (S1)
- At idle end the service unlinks its socket but holds `rerank.lock` until it exits (`rerank_service.py:219-227`).
- A search arriving in that window finds the lock held and sets `waited=True`. When the lock frees, `_start(waited=True)` raises. Its reason is `_refusal()`: the last REFUSED line in `rerank.log` (`rerank.py:92-113`), which may be days old, or just "rerank.log".
- So the search goes unranked when a fresh service could have started, and the reason may not name what happened.
- `scope: in`
- Ordinary work: yes, because the first search after a 15-minute lull can land in the second or two of shutdown. It is rare.
- Consequence: other. One search is unranked with a possibly wrong reason. It does not fail open or lose work.

**F3: stale "private" wording outside `allowed_paths`.**
- `retrieve.py:735`'s comment reads "(service, private)", and `docs/research/W2-112-shared-reranker.md:103` lists `"private"`.
- `scope: out`
- Ordinary work: no, because nothing reads them at runtime.
