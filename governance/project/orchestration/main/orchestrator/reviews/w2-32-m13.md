## Judgement rules (JUDGEMENT.md, word for word)

- **The threat model is ADR-0001's** (`docs/adr/ADR-0001-threat-model.md`): the Gov OS guards against honest agent mistakes, plausible accidents and drift in ordinary work, not against a deliberate adversary with the owner's privileges. Machinery against an adversary the design cannot stop produces endless review loops.
- **Every finding is judged by two questions, word for word:**
  1. "Can an honest agent hit this in ordinary work?"
  2. "Does it fail open or lose work?"
- **Only a finding with "yes" to both justifies a round.** A finding that needs a deliberate construction (a link planted at a protected name, git environment variables set by hand such as `GIT_OBJECT_DIRECTORY` or alternates, replace refs, an opaque interpreter used to evade the guard) is a row for the Wave 3 hardening pass, never a new round (DEC-801). A finding marked "no" on the first question is a row automatically.
- **Every finding in a probe or audit record carries two lines:** `Ordinary work: yes|no, because …` and `Consequence: fails open|loses work|other` (DEC-808).
- **No extra round on its own:** when a ticket will resume anyway, its accepted fixes ride along in that resume (DEC-802).
- **Feature-gated risks:** a risk that exists only when a feature is switched on is an entry criterion of the ticket that switches it on (DEC-803).
- **Packages:** every package that proposes a round states the classification of its findings on one line, before the recommendation (DEC-809).
- A finding blocks only if it is in scope, reachable in ordinary work, and fails open or loses work.

## Findings

### S8-F1 (M3): the closure facet's `capped` count is a lower bound
A dependent cut by the cap is marked known and never expanded, so its own dependents beyond it are neither reached nor
counted: the stand-in reports `capped: 60` where 70 are left out. The facet still says the walk was capped, which is
its purpose. Fix (rides along): count the cut ones' descendants, or name the facet "at least". The evidence row's
"at most 205 left out" figure for this repository may be low for the same reason.
- Ordinary work: yes, because the cap binds on 4 of this repository's records whenever the setting is on.
- Consequence: other (a count under-reported; nothing reached today is lost).

### S8-F2 (M3): the stating chunks go ahead of the named record's own chunks in the closure route
`routes[CLOSURE] = ahead + rest`: with the setting on, every walked dependent's stating chunk (hop 1's too) is ranked
before the start record's own chunks (for `DAEO-ym8a`, 24 ahead). For a question about the record itself rather than
its dependents, its closure rank falls (RRF 1/61 to about 1/85), which can lower the answer in the fusion. S8's record
half (the named record's 2 best chunks ahead after the rerank), when on, offsets it. The cap's choice by hop and id
cannot push out anything today's closure reaches; it only bounds the additions. Feature-gated (DEC-803): an entry
criterion of switching M3 on, that the visible-half run reports per-question ranks for the questions that name a
record, on against off.
- Ordinary work: yes, because every question naming a record with dependents takes this path once the setting is on.
- Consequence: other (a ranking effect, measured before adoption; nothing fails open).

### S8-F3 (M3): the close's incremental record load leaves the M3 index as at the last `gov rebuild`
`store.load_records` (W2-68, run at a close) rebuilds the record tables and refreshes the lexical and semantic
indexes, but not `closure_reverse_edge`; its `index_recipe` row stays `true`, so `walk` reads today's edges with the
stating lines of the last rebuild. A new edge's dependent is still reached, but its stating chunk is not put first; an
edited file's old line number can put another chunk of the dependent first. Fix (rides along): refresh it in
`_refresh_indexes` when the setting is on, or record the record store's digest beside the recipe and read a
different one as `stale`.
- Ordinary work: yes, because every close between rebuilds runs `load_records` when M3 is on.
- Consequence: other (an ordering staleness within reached records; no record lost, nothing fails open).

### S7-F4 (M1): a file text cut at `EMBED_CHARS` is not named, and a long headings line can push the opening out
`(header + headings + opening[:1200])[:EMBED_CHARS]`: a file with very many headings (the register: one per entry)
gets a vector of its path and headings alone, its opening cut, and the cut is not named in `refresh`'s `cut` or on
standard error as a chunk's is (S7, P-W2-32-8). At least one file of this repository reaches the 10,000 limit
(the copy's maximum). Fix (rides along): name file texts cut in `cut`, or bound the headings line so the opening
always survives.
- Ordinary work: yes, because the register is embedded and the setting on builds its file vector at every rebuild.
- Consequence: other (a weaker vector for one or few files, measured before adoption).

### S7-F5 (composition with M2, M4, M5): three conflicts, and `INDEX_FLAGS` means two things
`git merge-tree` conflicts in `loader.py`, `tests/acceptance/W2-32/README.md` (rows S7 and S8, both sides' notes) and
`test_w2_32_embed_headers.py` (two forms of one case), not one line. The loader's is a meaning conflict: on
`w2/W2-32`, `INDEX_FLAGS = (chunk_code_by_definition, chunk_register_by_entry, lexical_split_identifiers)` is the
keyword index's set, read by `lexical` for its recipe, its digest and which files a switch rechunks; on
`w2/W2-32-index`, `INDEX_FLAGS = (embed_headers, file_level_index, closure_reverse_depends_on)` is the set
`index_flag` accepts (any other key `ValueError`). Taking one side breaks the other (a `ValueError` from `index_flag`,
or M2/M4/M5 neither validated nor read); a union puts `embed_headers` (on in this repository), M1 and M3 into
`lexical_recipe`, so the keyword index's digest changes and switching M1 or M3 counts as a keyword-index switch.
Recommended resolution: keep W2-32's `INDEX_FLAGS` for the keyword index, add one tuple for every `rebuild.yaml`
flag (for example `REBUILD_FLAGS = (EMBED_HEADERS, FILE_LEVEL_INDEX, CLOSURE_REVERSE_DEPENDS_ON, *INDEX_FLAGS)`) used
by `_rebuild_settings` and `index_flag`, drop the separate `_check_embed_headers` call, and run both branches' suites
on the merge.
- Ordinary work: yes, because the CTO's merge of the two branches is the next step.
- Consequence: other (each wrong resolution either fails loudly or goes red in W2-32's own cases; none passes silently
  if both suites run).

### S7-F6 (M1, tests): no case shows the embedding policy or a role's filter on the file route
DEC-1065 (2)'s two rules hold by the code and by my probe, but neither the designer's nor the engineer's cases plant a
`not_embedded` file or a withheld path with the setting on. For the designer (rides along): a file whose namespace is
not embedded gets no file vector and no file hit; a role's withheld path never appears through the file route.
- Ordinary work: yes, because a regression here would come from ordinary edits to `_build_files` or the fusion.
- Consequence: other (a missing guard; today's code holds).

### S8-F7 (M3, a row): DEC-424's ahead rule now reads a larger `reached`
With `--ticket`, failure and lesson records in `reached` are moved ahead of the whole fused list; M3 enlarges
`reached`. No failure or lesson record has a `depends_on` edge in the store today (the sources are capability,
decision, plan, specification and task), so M3 adds none.
- Ordinary work: no, because it needs a failure or lesson record that declares `depends_on`, which none does.
- Consequence: other.
