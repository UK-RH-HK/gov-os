## Findings

**F1 — UNMARKED_CHANGE takes a changer that is PROPOSED (or REJECTED, WITHDRAWN) as an effective change.**
`check.unmarked()` never looks at the source's status. Planted: PROPOSED DEC-101 `**Supersedes:** DEC-100` gives
`add "SUPERSEDED by DEC-101" to DEC-100's status line`, and `--propose-marks` would print it; applied, an ACCEPTED rule
reads as superseded by a proposal (the loader's SUPERSEDES edge then drops it from current). On this repository one
instance: DEC-056 (DONE) `<- DEC-017` (PROPOSED), a free-text `replaced by` that in fact names an ONNX adapter, marked
`(text)`. W2-92's drift script has the same reading (no changer status filter), so S8's parity is unaffected. Fix to
ride along: skip, or list apart, statements whose source status is in NOT_IN_FORCE.
- Scope: in (S2, failure-4, the brief's "PROPOSED is never counted as current").
- Ordinary work: yes, because the register holds about 40 PROPOSED entries and a proposal stating `**Supersedes:**`
  or `**Changes:**` is the ordinary form of one.
- Consequence: other (a wrong mark in a printed patch the CTO reviews before applying; the tool changes no record).

**F2 — S16: the commit that closes a ticket is exempt whatever else it changes.** `ticket_changes()` skips any commit
where the ticket is open in the parent and `closed` in the commit (`check.py` line 802), so a closing commit that also
rewrites `kpis`, `allowed_paths` or `acceptance_tests` with no DEC id gives no finding (planted case above). The KPI
says a commit that changes an open or in-progress ticket's watched field with no decision id is
TICKET_CHANGE_UNMARKED, and only "a change of status, assignee or links **alone**" is exempt; DEC-1088 (6): "`gov
links` flags any change without one". The acceptance case pins only a status-only close. Fix (one line): judge the
watched fields of the closing commit as of any other commit (the status change itself stays exempt). Cost of the fix
in noise: 0 of the 152 closing commits in this history change a watched field unmarked.
- Scope: in (S16, DEC-1088 (6)).
- Ordinary work: yes, because the close is where an honest lead brings a KPI or a path list into line with what was
  delivered, in the same commit as `status: closed`, and that is the exact change DEC-1088 (6) wants flagged.
- Consequence: fails open (the unmarked scope change at close is never reported, listed or counted).

**F3 — S15's record: the main-tree measurement is still marked due.** `docs/research/W2-129-links.md` §1 and §7 say
the CTO's main-tree run is due; the CTO's facts (2.80 s, 2.83 s) are on the engineer's worktree. The KPI wants the
CTO's main-tree median of five recorded with its head beside the first `--all` counts. The CTO writes it at landing.
- Scope: in (S15).
- Ordinary work: yes, because the record is what the next pass reads for the baseline.
- Consequence: other (a record to complete; the times are well inside the bounds).

**F4 — S16 counts only `DEC-n` as a decision id.** `_DEC_ANY` ignores `ADR-n`, which the register's decision grammar
also admits; an ADR-marked change would be flagged (a false notice).
- Scope: in (S16).
- Ordinary work: no, because no ticket change here is marked by an ADR id alone.
- Consequence: other (a false notice, never a missed one).

**F5 — `--since` moves the mark.** A `--since <later rev>` run in a tree with an older mark writes HEAD as the mark,
so the next bare run lists nothing from the commits between the old mark and `<rev>`; they stay counted as standing.
The KPI allows it ("the head it judged") and failure-5 holds (counted, `--all` lists them).
- Scope: in (S10).
- Ordinary work: yes, because a lead and the CTO may run it in the same tree with different ranges.
- Consequence: other (listed less, counted in full).
