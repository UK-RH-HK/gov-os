## success-1: two detached halves, a build into the half not in use, a switch only on success, a search during a build answered from the ready half

What I checked:
- **The halves:** the halves are `<link>-a` and `<link>-b`, detached worktrees of the project's repository, outside the
  project. `building` is never the ready half: it is `second` when the link resolves to `first`, and `first` otherwise.
- **The switch:** the link is switched by `os.replace` of a fresh symbolic link, and only after `_faults` comes back
  empty. That needs all of these:
  - no `GovError`;
  - `lexical` and `semantic` both `recreated` (N-2);
  - the half's lexical index `fresh` and `semantic._status` None;
  - the half still at the head it was built for.
- **The semantic store recreated:** this check is included, as the brief asks. The unit test's three failure modes all
  leave the link where it was, with the ready half byte-identical: endpoint fails, model-less, and a stage raising.
- **A search during a build:** the refresh never writes the ready half. It reads it only through SQLite's backup
  (`mode=ro`), `_store_head` (`mode=ro`) and `git rev-parse`. Searches use `refresh=False` (`retrieve.py:217`), and
  lexical freshness compares the half's own tracked files with its own index. So a search through the link during a
  build is answered from the ready half, complete, and never `stale`. The unit and acceptance tests show this, and they
  pass on my re-run.
- **A killed build:** `seed.forget` runs at the start of every rebuild, so a half left behind has no record. It is
  never a warm base and never `unchanged`, and the next refresh seeds over it. The link is untouched. The unit test
  interrupts between the stages and the switch.
- **An unchanged head:** at an unchanged head the refresh does nothing: `_head(ready) == head` and the record names the
  running code. The unit test checks this byte for byte.
- **The lock:** an exclusive `flock` on `<link>.lock`, the same file `refresh_integration_store.sh` and the queue's
  promotion use. The lock order is the link's lock, then the rebuild lock. I found no deadlock with the queue: it uses
  per-tree rebuild locks through `rebuild_slot.sh`.

Findings:

- **F1: the branch's head is read before the lock, so a refresh that waited can move the link back to an older head.**
  - **The code:** `refresh` resolves `branch^{commit}` (integration.py:199) and only then takes `<link>.lock` (line
    203). A refresh that waits on the lock keeps the head it read before waiting.
  - **How it happens:** two refreshes can each be waiting with a different head: one started while another refresh was
    building, then a second landing, then another waiter. The kernel wakes `flock` waiters in no set order. If the
    later one wins, the earlier one then finds `ready` at H2, which is not its H1. It builds H1 into the other half and
    switches to it.
  - **Shown by P1:** after B had switched the link to H2, A's refresh logged `building store-a at <H1>, seeded from
    store-b` and then `-> store-a at <H1>`. The link ended at H1 while the branch was at H2.
  - **How long it lasts:** the store stays behind until the next update of `w2/integrate`, or the daily backstop.
  - **Why it is reachable:** `w2/integrate` takes commits minutes apart, and in bursts (five within 100 s at 15:30 on
    11-06). A seeded refresh takes 34 s to 4 min (`integration-store.log`). Three heavy slots let up to three refreshes
    in at once.
  - **The fix is small:** read the head after the lock is taken. Optionally, also refuse to build a head that is an
    ancestor of the ready half's head. With that, every refresh that waited builds the latest head, and the ones after
    it are `unchanged`.
  - Ordinary work: yes, because the hook starts one refresh per update of `w2/integrate`, and updates often come closer
    together than a refresh takes.
  - Consequence: other. Searches answer from a complete store of an older head. No guard opens and no work is lost.

- **F2: one search opens the store once per facet through the link, so a search that spans a switch reads both halves.**
  - **The claim:** the evidence says "A search that opened the link just before a switch finishes on the half it
    opened". That is not how it is built.
  - **What the code does:** `_store_root` returns the link path itself. Each facet then opens
    `<link>/.gov-runtime/store.db` on its own and resolves the link at that moment (`fusion.py:51`, `lexical.py:252`,
    `semantic.py:409`, `reverse_edges.py:167`, and the record routes).
  - **Shown by P2:** one `retrieve` opened `store.db` nine times. With the link switched after the first open, the
    halves were opened in the order `['a', 'b', 'b', ...]`.
  - **What is mixed:** both halves are complete, so this is not failure-2's "half-built store". But a bundle can join
    records and lexical or semantic hits from two different heads.
  - **The fix is one line:** resolve `GOV_STORE` once in `_store_root` (`os.path.realpath`). The link is still followed
    at each search, and the whole search then reads one half. That half is rebuilt only at the refresh after next.
  - Ordinary work: yes, because any search that is running at a switch hits it. That is rare per search, but common
    over a day of workers searching.
  - Consequence: other. One bundle is inconsistent across two complete heads. No guard opens and no work is lost.

- **F3: a refresh killed during its `git worktree add` or `git checkout --force` leaves a stale `index.lock`.**
  - **The lock:** the stale lock is in `.git/worktrees/<half>/`.
  - **The effect:** every later refresh then fails at `_checkout` with `REBUILD_FAILED`. This fails closed: the link
    stays and the log says why. But the store is frozen until someone removes the lock by hand.
  - **The window:** the checkout itself, about a second against a build of minutes.
  - **A possible fix:** before checking out, remove an `index.lock` that no live process holds. Or name it in the
    refusal.
  - Ordinary work: no, because it needs a kill (OOM, owner stop) inside the checkout's window of about a second.
  - Consequence: other. Fail closed; the store is not refreshed until the lock is cleared.

Verdict: **pass**.

## success-3 (widened): `gov launch` points every worker's retrieval at the integration store; a designer's retrieval never reads a ticket worktree's store

What I checked:
- **The variable:** `build_settings` sets `env.GOV_STORE` to the configured link for every role in `WORKER_ROLES`, and
  the CLI receives it both in `--settings` and in its process environment. A value that is set but cannot be used
  refuses the launch.
- **When `gov retrieve` reads it:** only when the command line gave no `--root`. `args.root` is None from the parser,
  and a direct call without `root` keeps its own root. An empty `--root ""` keeps the working directory.
- **No fall-back:** with `GOV_STORE` set and nothing at the place, the answer is `STORE_MISSING` for that place. It
  never falls back to the worktree.
- **The role filter:** it still resolves the main tree through `role_paths.main_tree` and looks tickets up in
  `[root, main]`. So a ticket that is not yet in the store's head is still found in the main tree. There is no new
  `ROLE_PATHS_UNREADABLE`.
- **N-4:** the cache write in `semantic._cache` swallows `sqlite3.Error`, and `_cached` opens `mode=ro`. A sandboxed
  session that cannot write into the half embeds its question again and gets the same answer. The engineer's statement
  holds.
- **Tests:** the unit tests (13) and acceptance success-3 (6) pass on my re-run.

Findings:

- **F4: `GOV_STORE` comes from the `rebuild.yaml` of the tree `gov launch` runs in, and many trees do not have the
  line yet.**
  - **Which trees:** the line exists only on `w2/integrate` since `a1d3e81a984c`. A worktree whose branch predates it
    carries no `integration_store`. That includes `w2/W2-116` itself: `a1d3e81a984c` is not its ancestor.
  - **The effect:** every session launched in such a worktree gets no `GOV_STORE`. Its plain search answers from its
    own working tree, which today means `STORE_MISSING`, the old behaviour. This lasts until the branch takes in
    integrate.
  - **Failure-1 today:** worktrees have no store of their own today, so nothing is answered from a ticket worktree.
    The failure-1 guarantee holds only because of that, and only for trees with the line.
  - **The options:**
    - read the place from the main tree (`role_paths.main_tree`), not the launch tree;
    - or have window 4's ACT say that in-flight worktrees search the store only after a merge from integrate.
  - Ordinary work: yes, because every worktree in flight at window 4 branched before the line.
  - Consequence: other. Those sessions keep today's `STORE_MISSING`. Nothing opens, because those worktrees hold no
    store.

Verdict: **pass**.

## success-4: refreshed after every landing; the warm base `--seed` reads; a seed behind the head is named; only what changed is re-embedded

What I checked:
- **The seed:** the refresh seeds from the ready half. The unit test uses an empty machine vector cache, and only the
  two changed texts are sent. A third head goes back into the first half, seeded from the second.
- **`_behind`:** it names `base_head` (40 hex digits) and the count, and says nothing at the head.
- **`--integration`:** it refuses `--seed` and `--no-embeddings`.
- **The hook:**
  - It fires only on `committed` and only for `refs/heads/w2/integrate`.
  - `setsid -f` with `</dev/null` and the output redirected returns at once and holds none of git's pipes, so it does
    not block the merge. Git ignores the hook's exit and an early-closed stdin in the `committed` phase.
  - It logs to `integration-store.log`, whose folder exists. `core.hooksPath` is not set, so `.git/hooks` is used.
  - The refresh's own checkouts move only the halves' `HEAD`, which does not match the hook's pattern.
  - Two landings close together are serialised by the lock, but see F1.
- **"The rebuild uses the code it runs under":** the build is in-process (`command.run` on the half). There is no
  `sys.executable` and no `PYTHONPATH` in `rebuild`, `retrieval`, `codeintel`, `store` or `secrets`. Being "unchanged"
  needs the record to name the running code, so after a re-pin the first refresh rebuilds. The re-pin also refuses the
  seed, which is the engineer's stated risk: the first refresh after a re-pin is unseeded. With the hook as written,
  though, "the code it runs under" is decided partly by the environment of whoever ran git (F5).

Findings:

- **F5: the hook inherits the environment of the git call that fired it, so the pinned `gov` can run another tree's
  code.**
  - **Shown by P3:** a commit made with `PYTHONPATH=/x/src` ran the hook with `PYTHONPATH=/x/src`. No `GIT_DIR` or
    `GIT_INDEX_FILE` was inherited at the top of the main tree, and the product's `git_env` strips them anyway.
  - **Why it matters:** `~/.local/bin/gov` is a venv entry point with no `-I`/`-E`. Run with
    `PYTHONPATH=<W2-116>/src`, the pinned interpreter imports `gov` from `<W2-116>/src/gov/__init__.py`.
  - **The effect:** any update of `w2/integrate` made by a process that exports `PYTHONPATH` makes the refresh build,
    and record, the store with that tree's code instead of the pinned code. The trigger can be a record script run as
    `PYTHONPATH=… python3 tool.py` that commits, the usual way to run tools under EMG's rule. The next refresh under a
    clean environment rebuilds it, because the code fingerprint differs.
  - **The fix:** start the hook's command with `env -u PYTHONPATH -u PYTHONHOME -u PYTHONSTARTUP -u GOV_REBUILD_LOCK`.
    That is the operator's ACT line, so it can ride along in window 4's ACT. Inherited `GOV_HEAVY_PRIORITY=1` from the
    merge queue is harmless either way.
  - Ordinary work: yes, because commits on `w2/integrate` are made by tool scripts as well as by hand.
  - Consequence: other. The store does not match the pinned code until the next clean refresh. Searches still answer
    from a complete store.

- **F6: hook-run refreshes that wait on `<link>.lock` hold a heavy slot while they wait.**
  - **Why:** `heavy_slot.sh` holds the slot's flock for the whole `gov` run, and that includes the wait on the link's
    lock.
  - **The bad case:** the first refresh after a re-pin is unseeded. Past cold builds took 1291–6077 s, and a few
    minutes with the machine vector cache. Two more updates of integrate during it fill the other two slots, which then
    sit idle for the whole build. The merge queue's and the closes' test runs wait meanwhile.
  - **The fix:** have the hook take `<link>.lock` (or a coalescing lock) before it asks for a slot. Or have a refresh
    that finds another one waiting exit, once F1 is fixed so that the waiter builds the latest head.
  - **Also:** the product's lines in the log carry no date, unlike the CTO script's lines. A `date` prefix in the hook
    would keep the log readable.
  - Ordinary work: yes, because updates of integrate during a long refresh are the norm.
  - Consequence: other. Throughput only.

- **F7: the merge queue's promotion builds the standby half with the clone's code (`PYTHONPATH=<half>/src`), so its
  record never names the pinned code.**
  - **The cost:** after each queue landing, the hook's refresh finds the promoted half not `unchanged`. It rebuilds the
    other half with the seed refused (the code fingerprints differ). The promotion's work is redone, unseeded.
  - **A guarantee cut short:** the previously ready half is rebuilt seconds after the promotion's switch. That breaks
    the "old half rebuilt only at the refresh after next" margin for a search running at that switch.
  - **Why it is out of scope:** the queue is the CTO's tool. Window 4's ACT should retire the promotion, or make it
    build with the pinned `gov`, once the hook is live.
  - Ordinary work: yes, because every queue landing does it.
  - Consequence: other. Repeated work and a shorter margin.

- **F8: a seed from a base that is ahead of the tree is still labelled `behind`.**
  - **What it does:** `_behind` sets `behind` for every base not at the tree's head. Its text falls back to "not at
    this tree's head (behind it, or on another line)".
  - **The ordinary case:** a worktree older than integrate, seeding from the integration store, gets
    `behind: "...behind it, or on another line"`, although it is the tree that is behind.
  - **The fix:** name the third case ("ahead of this tree's head by N").
  - Ordinary work: yes, because worker worktrees are usually older than integrate's head.
  - Consequence: other. A misleading message.

Verdict: **pass**.

  - **The change:** `_behind` counts both ways. It names `behind`, `ahead`, `diverged` or `unknown` under `relation`,

- **The hook line (F5, F6's slot order):** `setsid -f env -u PYTHONPATH -u PYTHONHOME -u PYTHONSTARTUP -u

### Round 2 findings

- **R2-F1: `gov retrieve --root <link>` still resolves the link once per facet.**
  - **The code:** with a `--root` given, `_store_root` returns it unchanged, so a search that spans a switch through an
    explicit `--root <link>` still reads both halves. P2: `['a', 'b', 'b', ...]`.
  - **Who uses that form:** the CTO's agents use it today: EMG's common rules say
    `gov retrieve --root /home/usain/gov-os-worktrees/W2-00-store`. Launched workers use the plain form, which is fixed.
  - **The fix is one line:** resolve the root in `_store_root` in both branches (`os.path.realpath` of the chosen root).
  - Ordinary work: yes, because the CTO's sessions search with `--root W2-00-store`.
  - Consequence: other. One bundle can join two complete heads. No guard opens and no work is lost.
- **R2-F2: the hook's `flock` runs without `-o`, so the outer refresh lock's descriptor passes down to `gov`.**
  - **The risk:** a process that `gov` leaves running and that inherited the descriptor would keep the refresh lock
    held after `gov` ends. Every later hook-run refresh would then queue behind it forever. Nothing would be wrong; the
    store would simply stop being refreshed.
  - **Why it is unlikely:** `gov` starts its children through Python's `subprocess` with the default `close_fds=True`.
    That includes the `ollama serve` it may start and the code-graph tool, so none of them inherits it today.
  - **The fix:** `flock -o`, which is what `heavy_slot.sh` uses for its slots for this very reason. It is one flag in
    window 4's ACT line.
  - Ordinary work: no, because it needs a lingering child that is started without closing descriptors, and the product
    starts none today.
  - Consequence: other. The store stops being refreshed until the lock holder is stopped.
- **R2-F3 (out of scope): a continuation token carries no mark of the half it was made on.**
  - **The effect:** page 2 of a search, asked after a switch, pages the other half with page 1's offset. The token

    pages, so this is not new with W2-116.
  - Ordinary work: yes, because a switch can fall between two pages.
  - Consequence: other. A page may skip or repeat items.
