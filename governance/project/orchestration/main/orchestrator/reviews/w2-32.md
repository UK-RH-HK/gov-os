## Judgement rules (JUDGEMENT.md, word for word)

- **The threat model is ADR-0001's** (`docs/adr/ADR-0001-threat-model.md`): the Gov OS guards against honest agent mistakes, plausible accidents and drift in ordinary work, not against a deliberate adversary with the owner's privileges. Machinery against an adversary the design cannot stop produces endless review loops.
- **Every finding is judged by two questions, word for word:**
  1. "Can an honest agent hit this in ordinary work?"
  2. "Does it fail open or lose work?"
- **Only a finding with "yes" to both justifies a round.** A finding that needs a deliberate construction (a link planted at a protected name, git environment variables set by hand such as `GIT_OBJECT_DIRECTORY` or alternates, replace refs, an opaque interpreter used to evade the guard) is a row for the Wave 3 hardening pass, never a new round (DEC-801). A finding marked "no" on the first question is a row automatically.
- **Every finding in a probe or audit record carries two lines:** `Ordinary work: yes|no, because …` and `Consequence: fails open|loses work|other` (DEC-808).
- **No extra round on its own:** when a ticket will resume anyway, its accepted fixes ride along in that resume (DEC-802).
- **Feature-gated risks:** a risk that exists only when a feature is switched on is an entry criterion of the ticket that switches it on (DEC-803).
- **Packages:** every package that proposes a round states the classification of its findings on one line, before the recommendation (DEC-809).
- Judge against ADR-0001's threat model (section 14): honest agent mistakes and plausible accidents in ordinary work, not deliberate adversaries. Ask of every finding, word for word: "Can an honest agent hit this in ordinary work?" and "Does it fail open or lose work?"
- Every finding carries two lines: `Ordinary work: yes|no, because …` and `Consequence: fails open|loses work|other`. A finding marked "no" is a row for the Wave 3 hardening pass, never a round; only "yes" with "fails open" or "loses work" fails the probe.

every hidden id is `h` and two digits (only the id shapes were read; 0 of 24 match `H\d+`). So a miss passed as

### Findings

**R2-F1 (S7).** Python's parents nest: `chunking.parents` gives the module as lines 1 to the end and each outermost
function inside it. `retrieve` drops a later chunk only when *its own* `parent_id` is in `x`, and leaves out of a later
parent only the children in `c`, never an earlier *parent's* span. So (a) a module expanded in one call, then a
function's chunk in a later call: the function's lines are sent again (and its parent expanded again); (b) a function
parent expanded first, then the module: the module sends the function's lines again. Neither is named in `repeats`.
My probe at `612cd0095c50` (a module chunk in call 1, a function chunk in call 3): `foo.py` 1-45, then 3-45, 43 lines
twice, `repeats` empty. The same happens within one call (1-45 and 3-45 in one bundle). The evidence's "both
directions now" holds for flat parents only. Fix (rides along, DEC-802): carry the expanded parents' spans (path,
first, last) in the token and judge a chunk and a later parent by lines against every span sent earlier, child or
parent, as `_without` already does for the children.
- Ordinary work: yes, because a paged retrieval about code often hits a file's module-level lines and one of its
  functions on different pages, and small files fit the budget.
- Consequence: other (tokens spent twice and the repeat not named; nothing lost, nothing let through)
