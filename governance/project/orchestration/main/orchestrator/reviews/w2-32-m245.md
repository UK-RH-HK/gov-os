## Findings

**S7-F1: with `embed_headers` on (this repository's setting), M5's whole entries can pass the embedder's read.**
`REGISTER_ENTRY_CHARS` (10,000) equals `semantic.EMBED_LIMIT_CHARS`, but `_Texts` prepends the header (path and
section trail, up to 600 characters in this register) before the cut. With M5 on, 4 of 1,394 register chunks pass
10,000 with their header (entries at lines 7566, 9912, 11119, 11347: 9,803 to 9,880 characters, headers 452 to 538),
so their last 300 to 400 characters are not embedded; the rebuild names them in `cut` and on standard error, so it is
not silent. The evidence's "so an entry is embedded whole" holds only with headers off. Recommendation: pack to
`EMBED_LIMIT_CHARS` less the longest header (a constant such as 9,400), or state the exception; for the CTO before
the measure that decides M5.
- Ordinary work: yes, because this repository runs with `embed_headers: true` and M5 is to be measured on it.
- Consequence: other

**S7-F2: with M5 on, a change of the path map's `decision_register` is not followed by the refresh.** The recipe
records `chunk_register_by_entry: true` but not which file; a path-map change re-judges every file (`JUDGES`), but a
file whose blob and verdict are unchanged is skipped (`stored.get(rel) == state and rel not in rechunk`), and
`rechunk` is empty since no key switched. The probe: the new register keeps its ordinary chunks and the old one its
entry chunks, while a build from nothing gives the reverse. No chunk is lost (every line is still indexed), nothing
is refused or opened. Fix if wanted: record the register's path as the key's value (`chunk_register_by_entry` =
the path), so a move is a switch and `_affected` names both files.
- Ordinary work: no, because the register's path is fixed (`docs/DECISION_REGISTER.md`) and moving it is an owner-level change, not ordinary work.
- Consequence: other

**S7-F3: a chunk id does not depend on its parent, so a vector survives a parent change that keeps the line span.**
`make_id("chunk", path, blob, first, last)`; `semantic._build` re-embeds only missing ids. With `embed_headers` on,
an M5 switch that changes a chunk's parent (and so its header) but not its span would keep the vector made with the
old header. Here 917 ids survive the switch and **none** has a different header text; it needs an entry above 10,000
characters holding a level 4-6 heading whose parts coincide with today's sub-sections.
- Ordinary work: no, because no entry of this register has that shape (0 of 917) and it needs both settings on and a sub-headed long entry.
- Consequence: other

**S7-F4: M4's search time is stated on the planted project only.** 1.81 ms against 1.79 ms on a handful of files;
the `parts` column adds about 3.2 M characters of postings on this repository (+7.8 %, confirmed), concentrated on
common identifier pieces (`path`, `id`, `root`, `rel`), which may lengthen the `_words` OR query's bm25 pass at
repository scale. Bounded in size, unmeasured in time at scale. Recommendation: the measure run that decides M4
reports the keyword route's time on the repository's store, on and off.
- Ordinary work: yes, because M4 on would apply to every search.
- Consequence: other

**S7-F5: M2's change acts in practice at top-level `class` lines only, and a class's decorators stay with the code
above it.** Functions and methods already start their own parents (`_functions`), so the cut before a `def` line
never falls inside a run; only a top-level `class` line inside a module run is cut (214 files, +654 chunks). The cut
is at `ast`'s `lineno`, the `class` line, so a decorator line stays at the end of the previous chunk (as today's
function parents already leave theirs). The form is the one the ticket states and the evidence says the cut acts on
the module's runs; noted so the measure's reading of M2 expects a small effect.
- Ordinary work: yes, because every decorated top-level class is chunked so with M2 on.
- Consequence: other

**S7-F6: the evidence row for M5 states the superseded form first.** Its first paragraph still reads "a longer entry
is split within it at that size, with the usual overlap" and "1,388" chunks; the re-scope paragraph after it states
the form the code has (own boundaries, no overlap, 1,394). A reader of the first paragraph alone takes the wrong form.
Recommendation: strike or mark the first paragraph as replaced by P-W2-32-11.
- Ordinary work: yes, because the evidence file is what the close and the next sessions read.
- Consequence: other

**S7-F7: the library's keyword search names an invalid setting as `unreadable`, not `CONFIG_INVALID`.**
`lexical.search` catches `GovError` and answers unavailable with reason `unreadable`; the code and key are named by
`load_config` (every command) and by `lexical.freshness`. It fails closed (no answer from a store built otherwise).
- Ordinary work: yes, because a mistyped value in `rebuild.yaml` reaches it.
- Consequence: other
