## Findings

**S6-F1. A store whose files were judged by code without S6, against a path map that already says `not indexed`,
keeps those files in the keyword index under S6's code. Neither the rebuild nor close's refresh puts this right, and
the report names nothing as kept out.** `_update` judges a file again only when its blob changes or one of the `JUDGES`
blobs changes (the path map, the gitleaks rules, `secrets.yaml`). The per-file verdicts carry no mark of which rules
made them. Probe 2 reproduced this three ways:
- (a) integrate's own code (S1-S5, the 3-column schema) builds the index with the policy map;
- (b) the head builds with no policy, the map gains the policy, and the pinned `gov` (`pin-9894b0cf`, which refreshes
  W2-13's 3-column store in place) refreshes;
- (c) the same as (b), with integrate's code doing the refresh.

In all three, the next refresh by the head leaves `fixtures/evaluation/q1.md` at `indexed = 1` with its chunks, and
returns `kept_out: {}`. The path map's blob is the one already recorded, so no file is asked again. `gov rebuild` is
incremental (it calls the same `refresh`), so it does not clear this either. The case is reached in ordinary work:
- `gov` on `PATH` is the pin until window 3's re-pin (R6 of the first review), and integrate's code is pre-S6;
- after D-7's map lands in a tree, the first `gov rebuild` run with either of them leaves this state. That includes the
  `gov rebuild` that `STORE_CODE_CHANGED` asks for once HEAD's code changes on the merge;
- every refresh by S6's code after that trusts it.

For this repository that means lens B's report, the one file D-7 newly excludes in practice (see the note), stays in
the keyword index. That is G4's contamination, with the rebuild's report saying nothing was kept out. The probe used
`lexical.refresh`, which is what `gov rebuild` and close call; no `gov rebuild` was run here.

Suggested fix, small, inside `lexical.py` and self-healing:
- in `_update`, work out `kept_out(root, list(current))` once per refresh (52 ms over this repository's 3,187 tracked
  paths with D-7's map);
- add to `asked` every path whose kept-out verdict disagrees with its stored `indexed`: kept out but not stored as
  `KEPT_OUT`, or stored as `KEPT_OUT` and no longer kept out;
- add a unit case that plants a stored `(blob, 1)` row with chunks under a `not indexed` namespace, with the current
  map's blob recorded, and asserts that one refresh drops it.

Another way would be a judging-version row in `lexical_file`, which also judges a store from before S6 once.

Ordinary work: yes, because the pinned `gov` and integrate's code are what ordinary `gov rebuild` and close runs use
until the re-pin. Once D-7's map is in a tree, the first such run leaves the state, and S6's code then never judges
those files again.

Consequence: fails open (the evaluation set's own document stays searchable by keyword, and the report names nothing
kept out).

**S6-F2. The path map's schema (`template/governance/kernel/schemas/path-map.schema.json`) does not name
`lexical_policy`.** The namespace object has no `additionalProperties: false`, so the field is accepted. But a reader
of the schema finds neither the field nor its two values, nor the rule that a `not indexed` namespace may not be
embedded. Row for product-spec (the schema is outside W2-13's paths).

Ordinary work: yes, because adopters and agents read the schema to write a path map.

Consequence: other (the validators refuse a wrong value, naming it; nothing opens).

**S6-F3. `core-pathmap` validates `lexical_policy` in the older list form of `namespaces`, but `kept_out` reads only the
mapping form.** A list-form map is not indexed at all: `gov.secrets.indexable` and `semantic._wanted` call
`.values()` on it and raise, so nothing is written. This therefore fails closed.

Ordinary work: no, because no path map in the repository or the template uses the list form, and the indexers cannot
index one.

Consequence: other.

**S6-F4. With the path map removed, `lexical.refresh` and `search(refresh=True)` raise `KeyError`** from
`gov.secrets.indexable`'s `load_config(root)["path-map.yaml"]`. This is integrate's code, unchanged by S6
(`kept_out` returns `{}` without a map, and nothing is widened or written). Out of scope.

Ordinary work: no, because `gov rebuild` and close check that the map is there first, and `gov retrieve` reads with
`refresh=False`.

Consequence: other (a traceback instead of `unreadable`; nothing is written).

### What the fix does (read from the code)

- `_update` works out `policy = kept_out(root, list(current))` once per refresh, over every tracked path.
- `asked` keeps its two old reasons (a `JUDGES` blob changed, or the file's own blob changed). It gains a third:
  `(rel in policy) != (stored[rel][1] == KEPT_OUT)`. `stored[rel]` is reached only when the stored blob equals the
  current one, so the row exists and nothing raises.
- `kept` is `policy` restricted to `asked`. A kept-out file is still neither scanned nor read. A row that changes
  verdict is dropped with its chunks (`stored.get(rel) != state`) and written again.
- Rows of untracked paths are dropped first. So after `_update` every `KEPT_OUT` row is a tracked path that `policy`
  names. `refresh` then names the rows from that same answer (`policy[rel]`) and no longer calls `kept_out` a second
  time.
- A stored `indexed = 0` (the filter refused it: a secret or the product memory class) that the map does not keep out
  agrees with the policy and is not asked again. A stored `KEPT_OUT` that the map no longer keeps out goes to
  `indexable(root, judged)`, the same secrets filter every new file goes through, and is indexed only if that filter
  lets it through.
- Side effect: `kept_out` (and so its `CONFIG_INVALID` on a bad `lexical_policy`) now runs on every refresh, not only
  when something is asked. Take a store whose recorded map, written by older code, holds an invalid value: S6's code
  now refuses it, naming the namespace, where round 1's code skipped it silently. This fails closed.
- Unchanged: the list form and a missing map still return `{}` (F3 and F4 as before), and `hits`, `ranked`, the
  schema, `freshness`, `search` and the rebuild's report shape are untouched.
