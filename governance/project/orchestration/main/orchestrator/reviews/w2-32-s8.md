## Judgement rules (JUDGEMENT.md, word for word)

- **The threat model is ADR-0001's** (`docs/adr/ADR-0001-threat-model.md`): the Gov OS guards against honest agent mistakes, plausible accidents and drift in ordinary work, not against a deliberate adversary with the owner's privileges. Machinery against an adversary the design cannot stop produces endless review loops.
- **Every finding is judged by two questions, word for word:**
  1. "Can an honest agent hit this in ordinary work?"
  2. "Does it fail open or lose work?"
- **Only a finding with "yes" to both justifies a round.** A finding that needs a deliberate construction (a link planted at a protected name, git environment variables set by hand such as `GIT_OBJECT_DIRECTORY` or alternates, replace refs, an opaque interpreter used to evade the guard) is a row for the Wave 3 hardening pass, never a new round (DEC-801). A finding marked "no" on the first question is a row automatically.
- **Every finding in a probe or audit record carries two lines:** `Ordinary work: yes|no, because …` and `Consequence: fails open|loses work|other` (DEC-808).
- **No extra round on its own:** when a ticket will resume anyway, its accepted fixes ride along in that resume (DEC-802).
- **Feature-gated risks:** a risk that exists only when a feature is switched on is an entry criterion of the ticket that switches it on (DEC-803).
- **Packages:** every package that proposes a round states the classification of its findings on one line, before the recommendation (DEC-809).
- Judge against ADR-0001's threat model (section 14): honest agent mistakes and plausible accidents in ordinary work, not deliberate adversaries. Ask of every finding, word for word: "Can an honest agent hit this in ordinary work?" and "Does it fail open or lose work?"

## Findings

**S8-F1 (S8, the symbol half's pool is not r01's).** In r01, `"code": "sem"` ranks the code route by cosine in
`_prepare` (`rx.py` 278-279), before the fusion (`_fusion` 359 → `_fuse`). The cosine-first hits therefore take RRF's
best code ranks and are likely on the 20-chunk page (radius 0: one round of 10, plus one). The product fuses the code
route in its own order (the spans' order, the harness's `set`; `retrieve.py` 263) and uses the cosine order only for
the front (375-377). So a cosine-first hit placed low in the route's own order can miss the product's page, and the
product then moves fewer chunks, or other ones, than r01 did. The rest of the page differs too. The evidence calls
the form r01's; it is r01's front without r01's fusion order.
Fix (rides along, DEC-802), or measure the half as built: when `code_first` is on and the code route answers, order
`routes[code]` by `_by_cosine` before `rrf(routes)`, and take the front from that order. That is the same single
`distances` call, made earlier. Off stays byte for byte.
- Ordinary work: yes, because every question naming a symbol takes this path once the half is switched on.
- Consequence: other (r01's gain may not carry over to the product; it is feature-gated, so it is an entry criterion
  of the measure that switches the half on, DEC-803)

**S8-F2 (S8, P-W2-32-9's record half is not s01's).** s01 (`"named_by": "rr"`) reranks **all** of the named record's
closure chunks (`rx.py` 261) and keeps its first 2 (272). `front` then keeps those of the 2 that are on the page
(401). The product ranks only the record's chunks **already on the page**, by the pool's scores, and takes the first 2
(`retrieve.py` 366-374). The two differ when the record's best chunk by the reranker is off the page. s01 then moves
one chunk or none; the product moves the record's next-best chunks that are on the page. P-W2-32-9's note, "the chunks
put ahead are on the page, so scored", is true of the product but does not make it s01. For records with few chunks
(most register entries, short records) the two agree.
Options (the CTO's, P-W2-32-9 being his ruling):
- (a) keep it, and have the measure test the product's form (the harness can mirror it as `named_by` over the page);
- (b) score the record's off-page chunks too, at the cost of a request outside the merged set (which P-W2-32-9 chose
  to avoid).

Recommendation: (a), confidence medium.
- Ordinary work: yes, because a question naming a long ticket, or a register entry of many chunks, has more of the
  record's chunks than reach a 20-chunk page.
- Consequence: other (a different chunk put ahead than the measured one; feature-gated, DEC-803)

**S8-F3 (S8, mis-recognition).** These are W2-92's recognisers, not changed here.
- **A symbol** is any word with an underscore or an internal capital (`_CODE_SHAPED`). It counts only when a
  non-test definition of that name exists. A plain word also counts when a cue such as "function", "class", "calls"
  or "defined" is in the question and the word is defined in `src` (for example `search` or `load`).
- **A record** is recognised three ways:
  - **An id in any token:** a path such as `tests/acceptance/W2-32/…` or `~/gov-os-worktrees/W2-32` names W2-32's
    ticket. A filename such as `DEC-1067.md` does not, because the token keeps `.md`.
  - **A title found whole, in any case:** 846 tracked titles, short ones among them, such as "gov context",
    "gov close" and "Session hooks".
  - **`--ticket`:** it always names its ticket.

**The bound:** with both halves at 2 and both misfiring, an answer at rank 2-5 can leave the top 5; with one half,
an answer at rank 4-5. The answer stays in the bundle; only its rank changes. The harness uses the same
recognisers, so the measure's figures already include these misfires.
- Ordinary work: yes, because questions quote paths and command names.
- Consequence: other (a quality risk on hit@5; nothing added, dropped or let through)

**S8-F4 (S8, the settings file).**
- A `routing:` block left empty (its keys commented out) is `CONFIG_INVALID`, while an empty file is off.
- An invalid file is raised after the rerank, so every `gov retrieve` in that tree is refused, with a named error,
  after the GPU work is done.
- The counts have no upper bound.
- A duplicate key resolves silently to the last value (the YAML loader's behaviour, the same as in the other config
  files).

Fix if wanted: read the settings before the routes, and treat `routing:` null as off.
- Ordinary work: yes, because commenting out the keys of a setting is a common way to switch it off.
- Consequence: other (fails closed and named)

**S7-F1 (S7, a question longer than the bound).** With `len(query) >= 24,000`, `room` is 0. Every text is then sent
empty, one per request, each request carrying the question's length, so a 30,000-character question gives
30,000-character requests.
- Ordinary work: no, because the questions are one line (`gov retrieve`, `retrieve_check`'s measure set), and
  `fusion.search`, the only other path, has no caller in `src/`.
- Consequence: other (one request above the size bound by the question's own length; the CTO's GPU backstop stands)

**S7-F2 (S7, the reranker's cut is not named).** A pair above the budget is read only up to it, so the tail of a
chunk longer than about 23,900 characters (less the path and the question) is not scored. Unlike the embedder's cut
(`cut` in `refresh` and `gov rebuild`), nothing names it. The evidence still carries the whole chunk. The tree's
longest line is 24,575 characters, and round 2 counted 10 lines over 10,000.
- Ordinary work: yes, because a question can land on that chunk, though seldom.
- Consequence: other (a score on a prefix; nothing dropped)

**S7-F3 (S7, R2-F2 grows with the character bound).** Requests are now split by characters as well. A page of
chunks above 12,000 characters goes one text per request, and with the shared service hung each request waits its own
`GOV_RERANK_TIMEOUT_S` (30 s) before the private reranker. The usual case is unchanged: 16 chunks of at most 1,200
characters, with a question under 300, still fit one request.
- Ordinary work: yes, because the service hangs at times, though a page of long chunks is rare.
- Consequence: other (latency)

**S7-F4 (S7, the character bound has no designer case).** The bound is guarded by the engineer's unit cases
(`tests/unit/retrieval/test_w2_32_whole_chunk.py` 40, 422-486). The designer's acceptance case
(`test_w2_32_s7_dec1067.py` 60) checks the 16 texts only. Fix: one designer case, in which a pool of long chunks gives
requests of at most 24,000 characters (`len(query) + len(text)`), in order, every candidate scored.
- Ordinary work: yes, because the close reads the acceptance suite, and a later change to `requests` is judged by it.
- Consequence: other (a weaker independent guard; the unit cases would still turn red)

**Rows kept:** R2-F1 (nested parents; its designer case is red until D-9, as stated). R2-F3 is closed by the
designer's `0223b7ea5757` (full requests of 16).

### What I checked, per line

- **S7, the padded bound on every reranker path (pass).**
  - **One gate:** `rerank.rerank` is still the only caller of a reranker's `score` in `src/` (`retrieve.py` 371;
    `fusion.py` 84, which no code in `src/` calls). Each request comes from `requests`.
  - **Both reranker processes:** `default_reranker`'s `score` sends a request whole to the shared service (`_ask`)
    or, failing that, to the private reranker. The service answers one request at a time, with no batching across
    requests (`rerank_service.py` 16). The worker scores a request with one `encoder.predict` call
    (`rerank_worker.py` 79), whose default batch of 32 holds any request of 16. So a request is one padded batch,
    which is exactly what the bound counts.
  - **S8 and the phrasings:** the record half reuses the pool's scores, and the code half sends no request
    (P-W2-32-9). The phrasings change the routes' lists, not the pool's size: the pool is still
    `fused[offset:offset + (rounds + 1) × batch]` (`retrieve.py` 298-299). So the merged pool has one rerank, in
    requests from `requests`. The designer's `test_the_merged_pool_is_reranked_once_within_16_texts_and_24000_characters`
    and the probe agree.
  - **The size:** the grouping takes the longest left and `min(16, 24,000 // longest)` texts. Every later text is
    no longer than the first, so count × longest ≤ 24,000 whenever the longest pair is ≤ 24,000. Grouping lengths
    longest first gives the fewest groups. The exchange argument: the group of the longest text holds at most
    `24,000 // longest`, and filling it with the next longest leaves only shorter texts for the other groups. The
    brute force agrees.
  - **The order:** each score goes back to its index, and the sort is stable over the pool. So the order is the
    unbatched one, with ties in the pool's order: the probe (5,000 tied pools), the engineer's unit case
    (`[100] * 40`, scores by length), and the off bundle byte-equal to `296a46393dd0` under tied scores.
  - **The margin:** the bound counts characters. The model pads tokens and adds about 80 characters of instruction a
