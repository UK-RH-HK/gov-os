## Findings

R1 (closed by `507df49a68f8`). The S4/F1 reference `TODAY` predated W2-112, so `test_u1`'s five cases failed only
on the added `rerank` key, and the continued page of `u1[batched]` went unchecked behind the first assert. The
revision pins `rerank` and nothing else. The continued page is now checked, and `gov accept` gives 30 of 30.
Ordinary work: yes, because every run of `gov accept W2-92` hit it before the revision.
Consequence: other (a false red against the tests' reference, not the code).

R2. The record route reads every record's frontmatter title once per process. That is 2.8 s on this repository's
1953 records for the first question of each `gov retrieve` process. The code route's `_defined` also reads every
non-test `.py` file of the store for each question that has a code cue.
Ordinary work: yes, because every CLI question is a new process.
Consequence: other (latency only, nothing lost or opened).

R3. Short record titles match plain questions by design: "gov close" matches DAEO-2lwj and "session hooks" matches
DAEO-zsvl. The question then takes that ticket's closure. The KPI asks for exactly this, but how precise it is
belongs to W2-61h's enlarged set and D-4b measure 1.
Ordinary work: yes, because many ticket titles are two words such as `gov <command>`.
Consequence: other (ranking quality, measured elsewhere).

R4. Take a question with an underscore or inner-capital word that is no symbol (`GOV_ROLE`, say) on a tree with no
code index. It gets `facets.code` unavailable and the stopping reason `FACET_UNAVAILABLE`, which is not today's.
With an index present, the route returns None and the bundle is today's.
Ordinary work: no, because the code index is built with every store rebuild, and the lexical route is missing too
without it.
Consequence: other (the answer fails closed and names the gap).

### What was checked

- **Titles and ids from one commit.** `_read_records` reads `HEAD`'s tree. It takes the string `title` from the same
  frontmatter parse that makes the `records` row `(path, id)`. `_load` writes `records`, `record_titles` and the rest
  in one transaction, and `load_records` goes through the same `_load`. So the titles are never the working tree's,
  and they can never be a different commit's than the ids. `graph_route._titles` runs one `SELECT path, id, title`
  on the store that `known` came from (the same `root`), and parses no file. Only a missing table or a sqlite fault
  gives None, and then it falls back to the files with `CSafeLoader`. An empty table gives `{}`, not the fallback.
  No other code writes `records`.
- **The schema change.** `record_titles` is left out of `_digest` (`_DIGESTED`), so a commit's digest and the
  recovery-rebuild check are unchanged, and `register_entries` is still the last table digested. `_TABLES` holds the
  new table, so `seed.schema_version()` changes and an old warm base is refused, with the difference named. The code
  fingerprint changes too, because `loader.py` is part of it. `gov rebuild --records` refuses with
  `STORE_CODE_CHANGED`, so a full rebuild is needed. Nothing is left half-built: the table is created and filled in
  `_load`'s single transaction, or not at all. A store built before S6 is not stale in a silent way either: it
  answers the way it did before S6, from the files and only faster (see R3). The only other caller of
  `_read_records` is `status/command.py` (`[2]`, the invalid list), and the new fifth element at the end leaves it
  unaffected.
- **`records/queries.py`'s join is unaffected.** `records` has no `title` column, and the `LEFT JOIN register_entries`
  is unchanged. The unit case `test_the_titles_leave_the_digest_and_the_joined_query_as_they_were` checks it.
- **S4, nothing else changes.** `retrieve.py` is not touched. `test_s6c` compares the bundles, item for item, with
  `BASE` `eb28c40866af` (git-archived `src/`) in 10 cases in a 240-record project, and all 10 pass.
- **The s6b revision `c83176227e88`** (independent test designer, `Rewrite-Reason` given) does not weaken the test. It
  refreshes the lexical index after the working-file edit, asserts the index is `fresh`, and asserts that the lexical
  route alone does not find the record by its old title. So only the record route can bring the record, and the case
  still fails for a title read from the working file (it is red on `w2/integrate`). The earlier form failed because
  of DEC-342 (a stale index cites nothing), whatever the title's source. That is consistent with the engineer's
  trace and the unit case `test_a_working_file_changed_after_the_index_leaves_no_chunk_to_cite`. `test_s6a`'s counter
  wraps `yaml.load`, and the fallback path calls that, so the case cannot be passed by changing the loader.

### What the verdict assumes about the real figure

The time clause of S6 passes on the code and the stand-in timing, if the CTO's measure 2 holds. That measure is the
median of ten cold `gov retrieve` runs of a plain question on this repository's store, on the shared servers. It
must be within about 1.2 s, measured on a store **fully rebuilt with the S6 code** (`record_titles` present). The
arithmetic agrees: S6 removes about 2.8 s from the first question of each process, and DEC-1065 described a slowdown
of about 4x over the pin's ~1 s, which leaves about 1.2 s. If the measure is above that, S6's time clause fails on
the measure, not on this code. With the table present, the record route's own cost is about 3 ms, so any remaining
time is spent outside `graph_route`.
