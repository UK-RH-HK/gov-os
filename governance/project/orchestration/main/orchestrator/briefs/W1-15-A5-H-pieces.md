### Piece 1 — the secrets-indexing check finishes on a real store (owner, DEC-595)

**What was measured.** In the main repository, on a quiet machine, `python3 -m gov.secrets` did not finish in 300 seconds, twice. Its runtime folder holds 238 MB in 2,575 files (the store 139 MB, the code index 87 MB). `stores_with_secrets` in `src/gov/secrets/__init__.py` scans every file under the runtime folder one after another, with up to two gitleaks runs per file, a SQLite file as its bytes and as its rows; the check runner (`src/gov/check/runner.py`, `_run_command`) gives every check a fixed 60 seconds. So `gov check` has a hard-block check that is red in any project with a built store.

**What is built, as the owner worded it:** the secrets-indexing scan runs its files in parallel, as the module already does for the indexer (`indexable` uses a thread pool), and a check's declaration may state its own time limit. **No rule is loosened; every file is still scanned.**

For the test designer:
- **The scan:** every file under the runtime folder is still scanned, with the same rules and the same two-configuration reading, and the answer is the same list in the same order as before, whatever the number of workers; a file that cannot be read, a folder that cannot be entered, or a gitleaks run that fails or passes its own limit still raises (nothing is let through undecided, and one failing file among many still fails the whole check). A planted secret or canary in any one file among many (first, last, in a SQLite row, in a large file) is found. Hold the time on a stand-in runtime folder of a stated size (many small files and one large SQLite file) with a bound that the serial form misses clearly; keep such cases few and declare in `tests/acceptance/serial-only.txt` only those that cannot hold under load.
- **The time limit in a declaration:** a check's declaration may carry a time limit in seconds (the designer names the key from the declaration schema's style and adds it to the schema or the reader that validates declarations, wherever declarations are validated today); a declaration without it keeps 60 seconds; a value that is not a positive whole number is refused as an invalid declaration (the stricter reading: refused, not ignored); a check that passes its stated limit is red with a message that names the limit that applied. Both layouts (template and installed kernel) read it the same way. `gov ci job` gets the same through the reader.
- **This check's declaration** states a limit. The designer proposes the value from the measurement the engineer makes on a stand-in of the main repository's size; it is to leave a clear margin and stay well under the close's own limits. Say in the return what `gov check` now costs in wall time for this check on a store of that size.
- **Not built (Wave 2 list, DEC-595):** scanning only changed files or caching results.

### Piece 2 — the template's rulesync hooks source (owner, DEC-596)

**What was found.** The kernel template's settings carry `"timeout": 60` on its three guard hook entries (DEC-580, merged). But a project's harness settings are generated by rulesync from `template/.rulesync/hooks.jsonc`, and that source has no time limit and **no entry for a failed tool call**: an adopted project runs no containment check after a failed command, which ordinary work meets.

**What is built:** `template/.rulesync/hooks.jsonc` gets `"timeout": 60` on every guard hook entry, and the missing entry that runs the containment check after a failed tool call (the same program the kernel template's settings register for it).

For the test designer (cases in W1-38's suite, which already generates from this source in a case's own temporary project):
- rulesync 24.0.0 passes both through: the settings it generates for Claude Code carry the limit on every guard hook entry and carry the entry for a failed tool call with the containment program. **If rulesync 24.0.0 drops the limit or has no name for the failed-tool-call event, that is a package at once** (with what it does generate), not a workaround by a hand-edited generated file.
- "Guard hook entry" as DEC-592 reads it: every hook entry that runs a program of the kernel's hooks folder; only the integer 60 counts.
- What the generated settings register agrees with what the kernel template's settings register, for the three guard entries.
- In a project made from the template, a session's failed command is followed by the containment check: hold it as far as the suites' existing live-hook cases reach (W1-05's live hooks, W1-46's live sessions) without a new kind of harness; if it cannot be held without a real session of a kind no suite starts today, say so and name it as the orchestrator's measurement on a dev-tier clone.
