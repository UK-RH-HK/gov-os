**Measured.** `gov check` reads the `policies:` block of the project's path map and wants a check for every key that is not `informational`. Today a key counts as covered only when its name happens to be part of some check's family name (`authority` in "authority/role limits", `context` in "context-reproducibility"). Five hard-block keys have no such name and are red in every project: `security`, `test`, `change`, `human_gate`, `tool` (finding `POLICY_NOT_COVERED`). The warning keys `memory` and `checkpoint` are yellow the same way. The one acceptance file that pins the rule is `tests/acceptance/W1-26/test_w1_26_policy.py` (its support holds the policy list).

**The owner's decision (DEC-613), word for word:** "Existing checks declare the policy they enforce. A policy key with no real check stays red and comes back to the owner as a package; no key is set to informational to pass."

**Built (DEC-620):**
- A check declaration may state the policy keys it enforces, in a list field named `enforces` (for example `enforces: [security]`). The field is optional; a value that is not a list of non-empty strings makes the declaration invalid, as any other bad field does. `gov check --list` shows it.
- A policy key is covered when, and only when, a declared check of the project states it under `enforces`. A family name that happens to contain the key no longer covers it: `authority` and `context` are covered because their real checks declare them. A key that is not `informational` and that no declaration states is reported exactly as today (red for hard-block, yellow for warning).
- **Which check declares which key is decided by evidence, not by name.** A check "really enforces" a policy only if a violation of that policy in a project turns that check red (or yellow for a warning policy). For each key the designer first reads what the policy is (the Charter and the Contract, `docs/contract/contract.yaml` around CAP-54 and the item the path map's comment cites, and the decisions they name) and what each of the twenty checks' programs verifies. For every pair (key, check) that is to be declared, **the designer writes a case that plants one violation of that policy in a temporary project and holds that this check is not green**. A pair for which no such case can be written honestly is not declared. Candidates to examine, none of them settled: `security` with the secrets-indexing check; `authority` with the authority check and the decision-citations check; `test` with the mutation-scope check; `change` with the claims check and the trailers check; `tool` with the adapter-portability check (it reads the tool registry); `context` with the context-reproducibility check; `checkpoint` with the fresh-agent-reconstruction check; `memory` with the index-freshness and retrieval-regression checks; `human_gate` with nothing known. Enforcement that lives in the guard or in `gov close` and in no check does not count: a check is what is declared.
- A key partly enforced (one kind of violation caught, others not) may be declared only if the designer's case shows the kind that is caught, and your return says in one line what is not caught: the orchestrator brings that to the owner.
- **Every hard-block key that ends with no declaring check stays red.** You list each in your return with what the designer found (what the policy asks, where it is enforced today outside `gov check`, why no check qualifies). That list is the owner's package; do not build a new check for such a key and do not change the path map.

For the designer, beside the pair cases: a key stated under `enforces` by a declared check is covered and not reported; the same key with the field removed is reported as today; a family name containing the key no longer covers it; an informational key with no check passes as before; a new key with no check and not informational is red as before; the invalid forms of the field are refused as a bad declaration. The case of `test_w1_26_policy.py` that repeats the family-name rule is rewritten to the declared rule, with a `Rewrite-Reason:` trailer.
