## The proposal (one, as the brief asks)
1. **The skill's check is a script in the skill's folder** (a skill folder may carry one, as
   `superpowers/systematic-debugging/find-polluter.sh` does; the copies carry it through rulesync):
   `template/governance/kernel/skills/spec-writing/check_spec.py`, Python 3 standard library only, run as
   `python3 <skill folder>/check_spec.py <spec.md>`. The SKILL.md's Done when names it.
   - **The spec's form** (stated in a reference file `spec-form.md`, one level down): one `##` heading per part:
     `Problem`, `Users and scenarios`, `Goals`, `Non-goals`, `KPIs`, `Test data`, `Out of scope`, `Open questions`,
     `Accepted by`. Each KPI line is a list item `- K<n>: <observable behaviour>` followed by a `Fails if:` line.
     The Test data section is a table, one row per source, with the columns `source`, `kind` (imported or synthetic),
     `owner`, `licence or recipe`, `privacy`, `secrets` (none, or how they are kept out), `hidden half` (yes, or n/a
     where it does not measure), `secured` (yes or no). Each open question is a package (question, options with
     cost, recommendation).
   - **What it prints and its exit:** one line per failed item, `REFUSED <part>: <reason>` (for example
     `REFUSED KPIs: K2 names code (parse_spec())`, `REFUSED Test data: row 1 has no owner`). It exits 1 on any such
     line. For a source with `secured: no` it prints `P1 Test data: <source> cannot be secured` and writes the P1
     package (question, options with cost, recommendation) beside the spec as `<spec>.P1.md`. It exits 2. It prints
     `PASS` only when every item holds, and then it exits 0. `PASS` is never printed with a REFUSED or P1 line.
   - **"Names code":** a KPI or failure line holding a code span, a call `name(`, a file path with an extension, or a
     dotted or snake_case identifier is refused.
   - The Done when lists the same items as yes/no checks, each one a line the script prints.
2. **The import record:** `template/governance/kernel/skills/spec-writing/imports.yaml` (the form of
   `superpowers/vendored.yaml`). Each imported part has an entry: `part` (path in the folder), `source`, `version`,
   `licence`. Copied text in a file is marked `<!-- imported: <part> -->`. `check_spec.py --imports <skill folder>`
   prints `REFUSED import <part>: no licence record` or `REFUSED import <part>: licence <x> does not allow the use`.
   The licences that allow the use are listed in the script: MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, CC0-1.0
   and CC-BY-4.0. It prints `PASS` only with every marked part recorded and allowed. The skill itself imports nothing
   (`imports: []`).
3. **F3's section half:** the acceptance test's own section grep (S4's verify already greps every section) carries
   the "Never section removed" case. The skill validator carries the size half (a 400-line body exceeds its 2,500-token
   cap: `SKILL_BODY_TOO_LONG` names the size). F3 is re-worded so it does not say "the skill validator naming the
   section".
