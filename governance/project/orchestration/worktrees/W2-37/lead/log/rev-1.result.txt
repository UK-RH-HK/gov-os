### F1 — MAJOR — The record graph reads `ok` when it does not match the working tree (makes a gate fail open)

**Case (a), uncommitted edits.** I loaded the store at HEAD, then without committing:
- added a ticket `PROJ-new1` that implements DEC-001;
- removed DEC-002's `depends_on: DEC-001`.

`gov impact DEC-001` then reported:
- `graphs.record: "ok"`;
- PROJ-new1 neither listed nor a gap;
- DEC-002 still listed;
- no word about uncommitted files.

`gov closure` on the same repo does report `uncommitted: ['.tickets/PROJ-new1.md', 'docs/adr/DEC-002.md']`.

**Case (b), branch switch.** I loaded the store on a branch where PROJ-ab01 had been replaced by PROJ-br01, then switched the temporary repo to an older branch that has PROJ-ab01. Impact reported:
- `graphs.record: "ok"`;
- PROJ-br01 listed, although that file is not in the tree;
- PROJ-ab01 dropped, although it is in the tree and implements DEC-001.

The cause: "current" only checks that HEAD is among the loaded commits, so an older commit passes. `gov status` uses the same rule.

In both runs `complete` was `false`, but only because no code index existed. The code index is copied from the working tree, so one built after these edits would read `ok`, and the report would then read complete. That last step is unreproduced.

**What should happen:** an uncommitted change under a record path, or a store loaded from a commit other than HEAD, should give a record graph that is not `ok` (stale) and `complete: false`. At least, the uncommitted files should be listed, as `gov closure` does.

- Ordinary work: yes, because changing a decision and asking its impact before committing is the KPI-1 flow itself, and switching branches after a load is routine.
- Consequence: fails open

### F2 — MAJOR — A CIT-E with an extra item, written as a single value or a map, is reported as matching (fails open)

The proposal had `code: []`. The CIT-E had `code: w37_orphan`, a single value instead of a list. `--compare` gave `matches: true, differences: []`.

The same happens with a map, `decisions: {DEC-099: done}`: `matches: true`. Any kind whose value is neither a list nor empty is silently dropped from the comparison.

When the proposal has items in that kind, the single-value form shows up instead as a false "only in proposal" difference.

**What should happen:** a kind that is not a list should be refused as malformed, or reported as a difference, never ignored.

- Ordinary work: yes, because writing one item as `key: value` instead of `key: [value]` is a common YAML slip.
- Consequence: fails open

### F3 — MAJOR — The CIT-P written by `--out` drops the report's incompleteness

`gov impact DEC-001 --out docs/citp/CITP-x1.md` with no code index:
- The printed result had `complete: false`, `graphs.code: "missing: …"`, and the gap `w37_apply: CODE_GRAPH_MISSING`.
- The file it wrote has only `change`, `radius: R3`, `depth: 8` and `affected` with `code: []`.
- The file has no `complete`, no `graphs` and no `gaps`.

So the saved CIT-P reads as a full assessment with nothing affected in code. Later `--compare` runs check CIT-Es against these lists.

**What should happen:** the file should carry the graph states, the gaps and `complete`, or `--out` should refuse while the report is incomplete. The README requires only `change`, `radius`, `depth` and `affected`, so no test catches this.

- Ordinary work: yes, because any project without a current code index that uses `--out` hits it.
- Consequence: other. The live report is honest; the persisted record misleads its readers (the owner's approval, the later CIT-E check), but nothing is lost and no gate opens at the time of writing. If the lead reads it as fail-open, it joins F1/F2 in the round.

### F4 — MINOR — The `--out` file name becomes the record id with no clash check

`gov impact SPEC-300 --out docs/impact/SPEC-300.md` wrote a CIT-P whose id is `SPEC-300`, the same id as the closed specification it assesses. After a commit and a store load:
- the store reported `invalid: []`;
- it kept the specification and silently left the CIT-P out;
- a `--compare` naming that CIT-P would be refused as "a specification, not a change-impact-proposal".

The same happened with `--out docs/citp/DEC-002.md` (id DEC-002).

**What should happen:** refuse a file name whose stem is an existing record id, or use the generated `CITP-…` id.

- Ordinary work: yes, because naming the impact file after the thing changed is natural.
- Consequence: other. The CIT-P silently never becomes a record; this fails closed.

### F5 — MINOR — `gov impact` is declared "read" but `--out` writes anywhere, unseen by the guard (role scope)

`--out` wrote, in turn:
- a file outside the repo through `../escape.md`;
- a file inside `.git/` (`.git/CITP-g.md`);
- a file through a dangling link, at that link's target.

The command declares `CLASS = "read"`, which by the CLI convention means "writes nowhere", so it cannot declare `ACT_PATHS`. The guard's Bash parser does not see the `--out` target, so an engineer can write a CIT-P outside their allowed paths. It never overwrites an existing file. The guard polices no `gov` command's writes (act commands included), so this predates the ticket.

- Ordinary work: no for the link, the `..` path and `.git/` (deliberate constructions); yes for a plain out-of-scope path.
- Consequence: other. A new file is added; no loss, no overwrite. This is a Wave 3 hardening row.

### Probed and found sound

- **Read-only:** a run without `--out`, including a closed-specification run, left every file outside `.git` (store included), HEAD, refs, stash, status and `.git/index` unchanged. `--out` added only its one file and refused an existing target.
- **Refusals stay refusals:**
  - no store gives `IMPACT_RECORD_GRAPH_MISSING`;
  - a zero-byte, truncated or garbage store, or one without the edges table, gives `IMPACT_RECORD_GRAPH_UNREADABLE`;
  - an empty change gives `IMPACT_NO_CHANGE`; a blank one gives `MALFORMED`;
  - an unknown id names the unreadable code graph;
  - a CIT-E whose `affected` is a list (not a map) is refused;
  - `--compare` together with a change or `--out` is refused.
- **Questions:** the exact form, `what is`, upper case and backticks run the assessment of exactly the id asked. Two ids, "changing X", "Whats", "What will be", curly double quotes and a trailing period are refused, never answered wrongly. Unquoted words are refused, naming them as unknown.
- **CIT-E comparison:** ids differing only in case, a misnamed kind, a missing item, an extra item in list form and an item without an id are all reported as differences.
- **Same sets as closure:** the record ids in impact's affected list plus its gaps equal `gov closure`'s set at the same depth for DEC-001 (depth 8), DEC-003 (depth 3, 60 links) and DEC-070 (a register entry, depth 1).
- **Scope:** all commits are within their allowed paths with the right `Role:` trailers; no `src/gov/closure` change; the acceptance tests are unchanged since the test designer's commit.
