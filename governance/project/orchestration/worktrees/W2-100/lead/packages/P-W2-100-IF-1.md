# P-W2-100-IF-1: W2-100's interface (the code-bound clauses of its KPI lines)

## Context
W2-100 (DAEO-uw5h, STANDARD, product-spec) writes four kernel skills (backend, api, data, security). Its paths are the
four skill folders and their `.rulesync` copies only. The ticket has no `## Interface`. The claim (e0960709) and the
brief give the work order, the scenario form (W2-11) and the import record (`governance/project/skill-imports.yaml`),
but not how six KPI clauses that name product behaviour are met. Read against the code at e0960709:

| KPI clause | What the code does today | Gap |
|---|---|---|
| S1, F1 (half), F3 (half): "a planted copy missing one of them [a section, a domain point] is named by the skill validator"; "a planted copy with the Never section removed ... fails the skill validator naming the section" | `src/gov/check/skill_validator.py` checks front matter (required keys, permission keys `allowed-tools`, `permissions`, ...: SKILL_PERMISSION_KEY), description ≤60 tokens, body ≤2,500 tokens (SKILL_BODY_TOO_LONG), `gov` commands. No section check, no domain-point check. | Validator is outside the paths |
| F1 (other half): "a planted skill copy with an allowed-tools or permission **line**" (in the body) | The validator names a front-matter key only, not a body line | Same |
| S2: "a planted engineer ticket naming the backend skill launches with the skill listed beside the engineer role in the launch record" | `src/gov/launch/role.py` marks skills `named: true` only from the role file's `- **Skills:**` line. A ticket cannot name a skill. Every loadable skill under `.claude/skills/` is listed `named: false`. The `.claude` copies come only by the copies ACT after the owner's yes. | Launcher and role file outside the paths. Cannot hold before the copies ACT |
| S4: "the scenario record holds three entries, each with a pass result and a **transcript summary**" | `gov skilleval` writes `scenario-records.yaml` (version, scenario, verdict, cause, cost, time), with no summary | Harness outside the paths |
| F4: "a planted history where the skill text is committed before its scenarios ... refused by the adoption check naming the skill" | `gov skilleval --adopt` checks the licence record and three passes only, for an **import** entry. No commit-order check, and no adoption step for a non-imported skill | Harness outside the paths |
| S6, F6: "the adapter check prints DRIFT naming the file" | `gov.adapters.portability` prints `SOURCE_DIFFERS` (a `.rulesync` copy) or `GENERATED_DIFFERS` (`.claude`), naming the file | Wording only |
| F2: "a planted copy of the skill that routes it as P2 fails the scenario and is refused" | Needs a real-model `gov skilleval` run of a planted copy. Acceptance cases cannot call a model (`-k "not real"`) | Where the evidence lives |

## Question
How are these clauses met within W2-100's paths, or does a clause move?

## Options
- **(a) Recommended: in-skill check plus re-wording, as W2-98's P-W2-98-IF-1 (DEC-1156 (5)).**
  - **I1:** one standard-library script, `template/governance/kernel/skills/<skill>/check_domain_skill.py`, in each of the four folders, byte-equal, so each folder stands alone and is copied with it (as `spec-writing/check_spec.py`). Run as `python3 <skill>/check_domain_skill.py <SKILL.md>`. It prints `REFUSED <skill>: missing <section|point>` or `REFUSED <skill>: permission line <n>: <text>`, exit 1. Otherwise `PASS`, exit 0. It checks the template's eight sections in order (Sources last), the five labelled parts (Conventions, Pre-commit checklist, Unit-test focus, Common mistakes, When to escalate), the area's named points (from a list in the script), a permission-granting body line, and for security a P2 or P3 route for a finding.
  - **S1/F1/F3 re-worded:** "named by the skill's own check (I1)". The validator keeps its front-matter permission key and size halves (as W2-98's F3).
  - **S4:** the summary goes in a hand-written `scenario-summaries.md` beside `scenario-records.yaml`, one entry per run (scenario, verdict, record's `run_at`, a three-line summary of the session's reply as `gov skilleval --json` returned it).
  - **F4:** the commit-order half is checked by the acceptance test's reading of `git log` on a planted history, plus the lead's `git log` evidence on the real one. The failing-scenario half is `gov skilleval`'s exit 3 (not adopted). It is not a new adoption gate.
  - **S2:** the grep half (no permission grant) and the guard half (same decision with and without the skill) are tested now. "Listed beside the engineer role" is re-worded to the record's `skills` list holding the skill (`named: false`) once the copies ACT has placed `.claude/skills/<skill>/`. It is checked after that ACT, not in W2-100's suite.
  - **S6/F6:** `DRIFT` reads as `SOURCE_DIFFERS` and `GENERATED_DIFFERS`, as W2-98's suite did.
  - **F2:** the planted P2 copy runs through the real `gov skilleval` (lead evidence, exit 3, recorded in the CIT-P), plus I1's refusal of a P2 route in the text.
  - Cost: about 100 extra lines (the script). No product code. KPI edits are the CTO's under DEC-1157 (12), listed for the owner. About 2 h. Real-model cost: 12 scenarios plus one planted F2 run, about 26 `claude -p` calls.
- **(b) Widen W2-100 into the product:** add a section and domain-point check to `skill_validator.py`, a ticket `skills:` field to the launcher, a summary field and a commit-order gate to `gov skilleval`, and a `DRIFT` alias. Cost: an engineer pair. It touches three shipped modules (W2-11, W2-60a, W2-104 code) and their suites (DEC-747 revisions). It is about 400 to 600 lines and 1 to 2 days, and it is a widening beyond "domain skills" (a split is the owner's, DEC-974).
- **(c) Defer the code-bound halves:** W2-100 writes the four skills and scenarios, and runs skilleval and the in-path greps. The six clauses above are marked "not in this ticket", and a later validator or launcher ticket takes them. Cost: none now. Five KPI lines are left part-met at close, which needs a DEC-105 re-baseline.

## Recommendation
(a), confidence high. It follows the owner's own precedent for W2-98 (DEC-1156 (5)). It keeps W2-100 inside its paths and its purpose. Every clause stays tested.

## What it blocks
The test-designer and implementer pair for W2-100. Neither started: the designer's cases and the implementer's
check script both depend on I1 and the re-wordings. Nothing was written or committed.
