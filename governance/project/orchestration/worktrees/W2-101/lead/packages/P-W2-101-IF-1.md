# P-W2-101-IF-1: W2-101's interface (the code-bound clauses of its KPI lines)

## Context
W2-101 (DAEO-6icv, STANDARD, product-spec) writes three kernel skills: frontend, ui-ux and devops. Its paths are
the three skill folders and their `.rulesync` copies only. The ticket has no `## Interface`, and the claim commit
(e0960709) changes only `status:`. The KPI lines match W2-100's word for word, except for the skill names and the
domain points. I checked them against the code at e0960709, and I get the same six gaps as W2-100's lead
(`~/gov-os-worktrees/W2-100/.gov-runtime/scratch/lead/packages/P-W2-100-IF-1.md`):

| KPI clause | What the code does today (checked) | Gap |
|---|---|---|
| S1, F2: "a planted copy missing one of them [a part or a domain point] is named by the skill validator"; "Never section removed ... fails the skill validator naming the section" | `src/gov/check/skill_validator.py` checks front-matter keys (`_PERMISSION_KEYS` gives SKILL_PERMISSION_KEY), description and body size, and `gov` commands. It has no section check and no domain-point check. | The validator is outside the paths |
| F1: "a planted skill copy with an allowed-tools or permission **line**" | The validator names a front-matter key, but not a line in the body | Same |
| S2: "a planted engineer ticket naming the frontend skill launches with the skill listed beside the engineer role in the launch record" | `src/gov/launch/role.py` sets `named` only from the role file's `- **Skills:**` line (SKILLS_LINE). A ticket cannot name a skill. Every other skill is `named: false`. The `.claude/skills/frontend/` copy comes only through the copies ACT after the owner's yes. | The launcher and role file are outside the paths, and the clause cannot hold before the copies ACT |
| S4: "the scenario record holds three entries, each with a pass result and a **transcript summary**" | `gov skilleval` (`src/gov/skilleval/harness.py`) writes `scenario-records.yaml` with no summary field | The harness is outside the paths |
| F3: "a planted history where the skill text is committed before its scenarios ... refused by the adoption check naming the skill" | `gov skilleval --adopt` checks only an import's licence record and its three passes. It has no commit-order check, and a skill that is not imported has no adoption step. | The harness is outside the paths |
| S6, F5: "the adapter check prints DRIFT naming the file" | `src/gov/adapters/portability.py` prints `SOURCE_DIFFERS` and `GENERATED_DIFFERS` and names the file | Wording only |

## Question
How are these clauses met inside W2-101's paths, or which clause moves? The answer to P-W2-100-IF-1 should apply
here too. One decision covers both tickets.

## Options
- **(a) Recommended: the same as P-W2-100-IF-1 (a) and the W2-98 precedent (DEC-1156 (5)).**
  - **I1:** one standard-library script, `template/governance/kernel/skills/<skill>/check_domain_skill.py`, in
    each of the three folders. It is byte-equal to W2-100's script, so each folder stands alone. It runs as
    `python3 <skill>/check_domain_skill.py <SKILL.md>`.
    - On a refusal it prints `REFUSED <skill>: missing <section|point>` or
      `REFUSED <skill>: permission line <n>: <text>` and exits 1. Otherwise it prints `PASS` and exits 0.
    - It checks the template's eight sections in order, with Sources last.
    - It checks the five labelled parts: Conventions, Pre-commit checklist, Unit-test focus, Common mistakes,
      When to escalate.
    - It checks each area's named points from a list in the script:
      - frontend: accessibility, state, browser support;
      - ui-ux: user flows as scenarios, reviewed by the owner;
      - devops: hermetic builds, pinned versions, rollback.
    - It refuses a body line that grants a permission.
    - The point lists for all seven areas live in the one shared script.
  - **S1/F1/F2:** re-worded to "named by the skill's own check (I1)". The validator keeps its front-matter
    permission-key and size halves.
  - **S4:** a hand-written `scenario-summaries.md` beside `scenario-records.yaml`, one entry per run, giving the
    scenario, the verdict, the record's `run_at` and a three-line summary of the reply from `gov skilleval --json`.
  - **F3:** the acceptance test checks the commit-order half by reading `git log` on a planted history, and the
    lead gives `git log` evidence on the real history. The failing-scenario half is `gov skilleval`'s exit 3, not
    adopted.
  - **S2:** the grep half and the guard half are tested now. "Listed beside the engineer role" becomes the record's
    `skills` list holding the skill once the copies ACT places `.claude/skills/<skill>/`. That half is checked
    after the ACT.
  - **S6/F5:** `DRIFT` reads as `SOURCE_DIFFERS` / `GENERATED_DIFFERS`.
  - **Cost:**
    - Work: about 100 lines of script, shared with W2-100. No product code.
    - KPI edits: the CTO's under DEC-1157 (12), listed for the owner.
    - Time: about 2 h.
    - Real-model cost: nine scenarios, about 18 `claude -p` calls.
- **(b) Widen into the product:** add a section and domain-point check to the validator, a ticket `skills:` field
  to the launcher, a summary field and a commit-order gate to `gov skilleval`, and a `DRIFT` alias. It touches
  three shipped modules and needs DEC-747 suite revisions. It is about 400 to 600 lines, 1 to 2 days and an
  engineer pair. It widens the ticket beyond domain skills, and a split is the owner's (DEC-974). If chosen, it
  belongs in one ticket shared with W2-100, not in both.
- **(c) Defer the code-bound halves:** write the skills and scenarios, run skilleval and the in-path greps, and
  mark the six clauses "not in this ticket". This costs nothing now. Five KPI lines would be part-met at close,
  which needs a DEC-105 re-baseline.

## Recommendation
(a), confidence high. It is the owner's own precedent (DEC-1156 (5)) and keeps W2-100 and W2-101 alike. Under (a),
W2-100 should make `check_domain_skill.py` first, or the CTO should name which ticket owns its bytes, so that the
three copies here are byte-equal to W2-100's four.

## What it blocks
W2-101's test-designer and implementer pair. Neither has started, and nothing is written or committed.
