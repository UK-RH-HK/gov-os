## What to build (the KPIs, and what the lead knows of the ground)

1. **One service process per machine (user):** the same pinned model, revision and environment as today (`MODEL`, `REVISION`, the interpreter at `HOME/.local/share/gov-os/reranker-venv/bin/python`, offline), in a new `src/gov/retrieval/rerank_service.py`, run by that interpreter. It listens on a Unix socket in the user's own folder (`~/.cache/gov-os/rerank.sock`, per P-RERANKER-1; the folder 0700, the socket 0600; no network port). It is started on demand by the first search that needs it, under a lock (an `flock` file beside the socket), so two searches starting together start exactly one service; it ends itself after a set idle time (P-RERANKER-1 suggests 15 minutes) and removes its socket.
2. **Many sessions at once:** requests are answered first come, first served, each caller getting its own scores for its own texts; a cap on a request's texts (the search reranks at most the bundle's candidate limit, `fusion.RERANK_TOP` = 30 chunks; a request beyond the cap is refused with an error, which the caller treats as "service down" for that search); a time limit per request. Batching several waiting requests in one model call is allowed only if the answers stay identical to a private reranker's; when in doubt, score one request at a time.
3. **The same answers:** the same model call as `rerank_worker.py` makes today (the same `CrossEncoder(...).predict(pairs)` on the same device), so the order and scores match a private reranker's on the same inputs and device; ties keep the given order (today's `rerank()` sort).
4. **Fallback, never failing, never hanging:** `rerank()` (or `default_reranker()`) tries the service first; if it cannot start, does not answer within about 2 s to connect (a cold start that loads the model may take longer: decide and state how the first search waits for the load, with a bound), times out, or answers with an error, that search falls back to a private reranker as today; where that cannot start either, the fused order is kept, with no scores (today's DEC-374 behaviour: the bundle's `merge.reranked` is false), and the reason is recorded. Each fallback is logged (a line in a log file under `~/.cache/gov-os/`, beside the socket, with time, reason and outcome), and a public function returns the fallback count so `gov status` can show it. **The private fallback never runs on the CPU** (the corrected KPI 7 on `w2/integrate`, DEC-1033: a CPU rerank takes over 100 s): it goes through the GPU slot rule; see item 6.
5. **The GPU budget (DEC-1032):** the embedder first (about 3.5 GB, pinned in the shared Ollama server), the service second (one copy, about 2.5 to 3.5 GB), at least 2 GB headroom, nothing else. **Before it loads, the service checks the GPU's free memory** (item 7c); if less than its share plus the 2 GB headroom is free, it loads on the CPU, says so by name (in its ready line, in every answer, in its log), and alerts (a log line marked as an alert). Never more than one copy on the GPU (the single-service lock gives this). The machine has one RTX 5070 Ti, 16 GB.
