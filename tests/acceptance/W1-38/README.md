Two rules hold for every case:

- **No source text is a stand-in written for the test.** Sources come from `template/.rulesync/`, the kernel

  rulesync *binary* (absent, hanging, failing, of another version).

## What was settled in round 3, and from where

1. **The version.** A project records the rulesync version it expects in the `rulesync` entry of
   `governance/project/tool-registry.yaml` (DEC-127: "the registry itself is per-repository project data";
   DEC-040: tools are installed "with a version pin recorded in `governance/project/tool-registry.yaml`";
   ADR-0002 §2 pins 24.0.0).
   No other file is a source for it: not `rulesync.jsonc`, not an environment variable. The check compares the
   installed rulesync with that entry. A registry that is absent, or has no rulesync entry, or names another
   version than the installed one, is not green and is the stated reason.
2. **Kernel against adapter source.** The kernel role and skill files are the authority (DEC-066: roles are
   "generated by rulesync from kernel role files"; W1-33 and W1-35 deliver them); the files under
   `.rulesync/subagents/` and `.rulesync/skills/` derive from them. The check compares each pair in the project.
   A finding names the rulesync source (the derived file) and no file outside the pair.
3. **OpenSpec commands.** rulesync holds them as sources. DEC-074 Q7: "rulesync owns `.claude/`; OpenSpec and
   vendored skills registered as rulesync sources". Measured with rulesync 24.0.0 in a temporary folder:
   `generate --delete` removes every file under `.claude/commands/` and `.claude/skills/` that has no rulesync
   source, so commands that OpenSpec writes there by itself do not survive it (KPI failure 1). The registered
   source of a command is therefore the text OpenSpec ships: what `openspec init --tools claude` of the registered
   version (1.13.2) writes under `.claude/commands/opsx/`, which is six files: `apply`, `archive`, `explore`,
   `propose`, `sync`, `update`. `rulesync import` followed by `rulesync generate` gives each of them back with the
   same body and the same frontmatter values (measured), so the comparison below is reachable. A command text
   written for this ticket fails it.
4. **Behaviour in place of file-exists.** See the tables: the declaration and the module are measured through
   `gov check`; CLAUDE.md and AGENTS.md are compared with the root rule.
5. **Findings.** Read from the check's entry in `gov check --json`.
6. **OpenSpec skills (round 3b, DEC-468).** The six skills `openspec init --tools claude` of the registered version
   writes under `.claude/skills/` (`openspec-apply-change`, `openspec-archive-change`, `openspec-explore`,
   `openspec-propose`, `openspec-sync-specs`, `openspec-update-change`; one `SKILL.md` each) are registered rulesync
   sources, unchanged, like the six commands. Measured with rulesync 24.0.0 in a temporary folder: `rulesync import`
   followed by `rulesync generate --delete` gives each of the six back with the same body and the same frontmatter
   values, so the comparison is reachable. A skill text written for this ticket fails it.
7. **Who refreshes the sources (DEC-469).** The ticket that changes the `openspec` or `rulesync` entry of the tool
   registry refreshes the registered sources from that version in the same change; it needs no case here.

### The settings file

The generated `.claude/settings.json` of the project holds what the two sources give and nothing else. A key the
sources do not give is a hand edit, whatever rulesync does with it when it writes the file again. Measured: rulesync
rewrites only the parts it manages (the hook events, and the permission rules of the tool categories the source
names, here `Bash` and `Edit`) and leaves every other key as it finds it. So its own check sees a hand-added
`Bash` rule or hook entry and does not see a rule of another tool, another key under `permissions`, or another
top-level key. The cases write the file back as rulesync writes it (two-space JSON, final newline; asserted), so
the added or removed key is the only difference.

A key that another owner needs in the committed settings (for example the `Read` deny rule built from
`held-out.yaml`, DEC-162) reaches the file through a rulesync source, or it is a finding. No case here names such
a key.

### A role's tools

The kernel role file is the authority of a role's limits (DEC-066, W1-33). The tools of
`.rulesync/subagents/<role>.md` are its `claudecode.tools`. The tools a kernel role names are the Claude Code tool
names that occur as whole words, in this case, in its **Tools** field; the names looked for are `Agent`, `Bash`,
`Edit`, `Glob`, `Grep`, `NotebookEdit`, `Read`, `Skill`, `Task`, `TodoWrite`, `WebFetch`, `WebSearch`, `Write`.
The two are compared as sets (order is free). rulesync generates the definition's `tools` from the source
(measured), so source and generated file never differ; the difference to find is source against kernel.

**Found while writing the cases:** `template/.rulesync/subagents/independent-auditor.md` lists `Read`, `Grep`,
`Glob`, `Bash`; the kernel role's Tools field names those four and `Write`, `Edit` ("for its report only"),
`WebSearch`, `WebFetch`. That is a difference between adapter source and kernel in the delivered sources. See
package P-5.

## The one tolerated difference between a source file and its generated file

rulesync rewrites the frontmatter (key order, quoting, folded lines) and **drops the blank lines between the closing
`---` of the frontmatter and the first line of the body**. Nothing else is tolerated: after that point the body is
compared byte for byte. Frontmatter, where a case compares it, is compared as a parsed mapping. The six OpenSpec
skills are compared with this same tolerance and no other: the body of `SKILL.md` byte for byte after that point,
its frontmatter as a mapping (as for the OpenSpec commands).

**The kernel skill files stay as W1-35 and W1-36 left them**, with their blank line after the frontmatter. The
eight edits of the last run that removed it are undone by the engineer; `test_skill_body_matches_source` holds with
the kernel files unchanged, because the tolerance is in the comparison and not in the kernel.

## Packages

P-1 and P-2 are decided: P-1 by DEC-468 (option a; its cases are `TestOpenSpecSkills` and
`test_delete_preserves_openspec_skills`), P-2 by DEC-469 (the recommendation). They are kept below as raised.

**P-1. The six skills OpenSpec writes beside its commands.** (round 3; decided by DEC-468)
- Question: must the skills `openspec init --tools claude` writes under `.claude/skills/` (`openspec-apply-change`,
  `openspec-archive-change`, `openspec-explore`, `openspec-propose`, `openspec-sync-specs`,
  `openspec-update-change`) be registered rulesync sources too?
- Why now: KPI success 1 names "OpenSpec commands" only; KPI failure 1 says "removes OpenSpec or vendored skills",
  and DEC-074 Q7 says "OpenSpec and vendored skills". Measured: `generate --delete` removes all six skills, as it
  removes unregistered commands.
- Options: (a) register the six skills as sources beside the six commands; (b) commands only, and the project does
  not use OpenSpec's skills.
- Impact: (a) six more source files, about 92 kB, and one more parametrised case here; (b) none here, but after
  the first `generate --delete` the skills `openspec init` wrote are gone.
- Reversibility: high. Recommendation: (a), since rulesync owns `.claude/` and a later `openspec init` or
  `openspec update` would otherwise write files that the next `--delete` removes. Confidence: medium.

**P-2. Who refreshes the registered OpenSpec sources when the registered OpenSpec version changes.** (round 3; decided by DEC-469)
- Question: when the registry's OpenSpec version changes, is refreshing `template/.rulesync/commands/opsx/` part of
  that install's ticket?
- Why now: the cases compare with the installed, registered OpenSpec, so a version change turns them red until the
  sources are refreshed. That is the intended signal, but no source names the owner of the refresh.
- Recommendation: the ticket that changes the registry entry refreshes the sources in the same change.
  Confidence: medium.

**P-4. Paths directly under `.claude/` that no source gives to an owner.** (round 4; open)
- Question: is a file under `.claude/` that is outside `agents/`, `skills/`, `commands/`, is not `settings.json`,
  and is not `settings.local.json` or under `worktrees/`, a finding of the check? Examples: `.claude/notes.md`,
  `.claude/hooks/x.py`, `.claude/rules/x.md`, `.claude/output-styles/x.md`, and files Claude Code writes there by
  itself (`.claude/scheduled_tasks.json`; a `.claude/.cc-writes` folder was seen in this session).
- Why now: ADR-0002 §5 says "rulesync owns .claude/", which read alone makes every such file a finding; DEC-063 and
  DEC-050 name two exceptions and no source lists the others. The round 4 cases cover only the paths the sources
  state.
- Options: (a) everything under `.claude/` needs a source except the two named exceptions; (b) only the three
  folders and `settings.json` are checked, the rest of `.claude/` is left alone; (c) as (a), with a list of further
  exceptions kept in project data.
- Impact: (a) the check turns red in any project where Claude Code itself has written a file under `.claude/`,
  which no ticket has measured yet; (b) a hand-written `.claude/rules/` or `.claude/hooks/` file, which Claude Code
  may load, is not found; (c) one more file to keep.
- Reversibility: high (one more case here, one more comparison in the check).
- Recommendation: (b) for this ticket, and (a) or (c) decided after W1-42 has measured what a live session writes
  under `.claude/`. Confidence: medium.

**P-5. A role's tools: equal to the kernel role's, or within them.** (round 4; open, cases written for "equal")
- Question: must `claudecode.tools` of a role's adapter source be exactly the tools its kernel role names, or may
  the source name fewer?
- Why now: the brief for round 4 says a source "whose tools differ" is not green, and the cases are written for
  that reading. The delivered auditor source already differs: four tools against the kernel's eight (it lacks
  `Write`, `Edit`, `WebSearch`, `WebFetch`).
- Options: (a) equal: the auditor's source gets the eight tools the kernel names (the guard and the launcher keep
  its writes to the report path, DEC-112); (b) within: a source may narrow a role, and only a tool the kernel does
  not name is a finding; (c) the kernel role's Tools field is changed to the four (W1-33's file, outside this
  ticket's paths).
- Impact: (a) one line in `template/.rulesync/subagents/independent-auditor.md`; without `Write` and `Edit` the
  auditor as a subagent can write its report only through Bash. (b) removes
  `test_source_without_a_tool_the_kernel_role_names` and turns `test_source_tools_are_the_kernel_role_s` into a
  subset comparison; a source that silently drops a tool is then not found. (c) a W1-33 change and its tests.
- Reversibility: high. Recommendation: (a): the kernel is the authority, and "generated adapters match their
  source" (KPI success 3) is a statement of equality. Confidence: medium-high.

## Test design

- Token counting: `math.ceil(len(text) / 4)`.
- Field comparison uses W1-33's whitespace-collapsed labelled-field reader.
- "Files named" by a text are the files of the temporary project whose relative or absolute path occurs in it.
- Round 4's hand edits are made in the temporary project after generation; where the edit is of a source
  (the role's tools) the project is generated again, so rulesync's own check is clean (asserted).
- A stand-in rulesync binary is written outside the project; where it only changes one answer (the version), it
  hands every other call to the installed rulesync.
