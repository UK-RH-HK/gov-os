# W2-121 acceptance tests: `gov dispatch tick` and `gov dispatch status` (part a)

Ticket DAEO-cb2b (W2-121 part a), profile FULL, class C2. Written by the independent test designer (MR-3) from the
ticket's KPI lines S1 to S10 and F1 (start half) and its Interface section, with the lead's reading of the Interface
(brief td-1), before any implementation: the code read is `w2/integrate`'s (`src/gov/cli/main.py`'s convention, the gate's
`gov.resources`, the launcher's `build_lead_settings`, `gov plan --ready`), never this ticket's branch.

## How they run

    env HOME=<an empty folder> PYTHONUSERBASE=$HOME_REAL/.local PYTHONPATH=<worktree>/src \
      python3 -m pytest tests/acceptance/W2-121 -q -p no:cacheprovider -o tmp_path_retention_policy=failed \
      -m "not local_only" -k "not real and not green_here and not time_limit"

About 40 s for the 130 cases (a few seconds each at most: a child process per `tick`, the stubs, no model, no network).
The filter leaves out nothing: no case is named with `real`, `green_here` or `time_limit` and none is marked
`local_only`. (`PYTHONUSERBASE` is only so that an emptied `HOME` still finds pytest in the user site.)

## What is planted (never the real HOME, `~/.claude`, `~/gov-os-worktrees`, the real `/proc` for counting, or a session)

Everything is under the test's `tmp_path` (`w2_121_support.Project`):

- a project root that is a git repository on the branch `integ`, a worktree per W2 (`git worktree add`, branch
  `work/<W2>`), `.tickets/<id>.md` with the claim committed as each case needs (on both, on the integration branch only, on
  the worktree only, on neither), briefs, `governance/project/dispatch.yaml`;
- a tmp `HOME` with W2-20's `gate.json` (`gov.resources.config.template()` with the floor and working size set per case) and
  the `GOV_RESOURCES_*` variables (`MEMINFO`, `LOADAVG`, `NPROC`, `BUSY_CORES`, `DISK`, `PROC`, both embedding readings);
- a planted `/proc` folder: `<proc>/<pid>/cmdline` (NUL-separated, `--settings` JSON with `GOV_ROLE` and `GOV_TICKET` as
  `gov launch lead` builds it), `stat` and `statm` (so that W2-20's own reader sees the process too, with a resident size);
- two stub programs: the **launch command** (`launch_command` with the placeholders `{ticket}`, `{w2}`, `{brief}`, `{log}`;
  it records its argv, stdin, pid, session id and the `started.txt` it saw to a file, prints a planted output, sleeps and exits
  with a planted code) and the **notifier** (`notifier_command`; it records its argv). A detached launch is waited for with a
  bounded poll, never a bare sleep; a session a stub left running is killed by pid (only a pid still running one of the
  test's own stubs) when the test ends;
- `python3 -m gov.cli.main dispatch tick|status --root <project>` runs as a child process with the tree first on
  `PYTHONPATH` and no `GIT_*` or `GOV_*` variable of the session running the tests. A hung `git` is a stub `git` first on
  the child's `PATH`.

## The interface the tests assume (brief td-1's reading; where the ticket is silent)

State folder `<root>/.gov-runtime/dispatch/`; configuration `<root>/governance/project/dispatch.yaml` (`dispatch:`);
exit codes 0 (a pass done, or nothing to do, or entries skipped for the stagger or `max_leads`), 3 (the gate or the forecast
refused a start), 4 (the lock held: the second pass writes nothing), 2 (a usage or configuration error, the key named);
`tick.lock` is a `flock`; an `OFF` file stops everything but the status; the log name is in `started.txt` before the launch
is spawned; a session is finished when `<state>/logs/<log name>.exit` exists; an inbox item's first lines are `log:`, `W2:`,
`status:`; an unread item is in `inbox/`, a read one in `inbox/read/`; history lines are `{"kind", "at", "cpu", "mem_bytes"}`.
**Key names inside `status.json` and `peaks.json` are the engineer's:** the tests find a section by a part of its key
(`running`, `load`, `mem`, `gate`, `slot`, `ahead`, `queue`, `inbox`, a kind's name for its peak) and read its figures
(a figure may be written in bytes, KiB, MiB, GiB or as text; a time as an ISO-8601 string). The reason a skipped entry is
named with is found by words (`claim`, `clean|dirty|modified|tracked|uncommitted|change`, `brief|slot|@@|empty|missing`,
`running|already`, `unread|return|inbox`, `gate|memory|shut`, `disk`, `stagger`, `max_leads|leads`, `malformed`,
`no room for its peak` with figures in the same entry's text, `review|probe|round|owner`), in the smallest part of the
status that names the entry (its log name, its W2 id or the line's own words).
