## 3. Other changes I propose to the draft

1. **Name the scheduler (W15).** Steps W3 (retry), W4 (weekly), W16 (weekly hygiene) and rule 4 ("a scheduled check") all need a thing that runs on a schedule; no step names it, the crontab is the CTO's and the owner's hand-kept file, and the kit installs none. Reason: three steps and a rule depend on it and none holds it (SQ-5).
2. **Add the full regression to a step.** The draft has no step for the nightly full regression: W11 runs the *selected* tests, W13's acceptance names the proving run and the memory measures. The patch release's G2 reads a nightly record (`release/gates.py:112`). Propose it in W16 ("weekly hygiene": the full regression record) or as a second part of W11 (`gov queue --full`). Reason: a gate reads what no step produces (SQ-8).
3. **Add the handover to W8 or W15.** Rule 10's handover (CTO and senior engineer start fresh each morning) has no step: `start_cto.sh` demands a handover file, and its form is checked by nothing (audit 4 B14, B15; SQ-13).
4. **Merge W2 and W3 in the table's text.** One tool, `gov rebuild`, builds the store (W2) and refreshes it (W3); W3 differs only in its trigger and its retry. Keep two rows for the owner's reading, but one tool column. (A presentation point; I would not change the numbering.)
5. **Make the "Today" column computed, not typed.** Four of the 16 cells were already out of date within hours of the audit (first queue landing, `models-rubric` merge, the connectors key, `fixes-015b`). Once A-23 (the enforcement field) exists, `gov status` can print the Today column from it; until then the CTO re-reads it at each release (golden workflow §3 says every release prints the counts).
6. **Print three measures in §3's baseline.** §3 gives 21 / 13 / 31 / 19 / 16 %, which are Contract items by class (audit 4 §0). The step view in `TOOL-MAP.md` section 3 is 1 on, 11 partly, 4 off (6 / 69 / 25 %); the rows' view is 29 % on, 21 % partly, 49 % not. Propose that each release prints all three, since they measure different things (items, steps, tools), and that §3 says which is the "90 %" target (§3 says "the flow 90 % or more held by code": the step view is the one that reads as "the flow").
7. **State where a tool lives in rule 3 by a test.** Rule 3 (a tool outside the product is absorbed, replaced or retired) has no test for "outside". Propose: a file that `gov update` would not carry to an adopted repository is outside; today that includes the one live git hook (`.git/hooks/reference-transaction`), every cron line, `~/.local/bin/ollama`, `agent_model.py` and the scratch folder (map rows 6, 7, 11, 12, 57, 81).
8. **A rule 9-bis or a W1 check for "too small".** Rule 9 says a machine too small is refused; the code refuses only a launch. Propose the same refusal at adoption (W1) and at install (W14), or soften the rule to match.
9. **Drop `gov close` and `ESCALATION_AT` from the story.** Rule 3's two rounds are contradicted by code the draft never mentions; naming `gov close`'s retirement in W11 closes it (A-18).

### SQ-1. What is the first slice of rule 8's decision machinery, and does the owner's push stay Claude Code's own?
- **Found:** rule 8 and W5 say each decision is a structured record whose fields set its level, code refuses a decision below it, routes owner decisions to a page, writes the answers into the register, and the owner is pushed for stoppers. `decisions/command.py:36-52` has `basis` and `in-force`; the record template has no level field; no code writes a page or a push; `owner-ping` appends to a log nobody reads; the proposal is `proposals/DECISIONS-BY-PAGE-SPEC.md`. The owner's phone push is today Claude Code's own (`agentPushNotifEnabled`, `~/.claude/settings.json`).
- **Options:** (a) build all of rule 8: three record fields, the level computation, the refusal, `gov decisions answer`, a page generator, a push (L, several tickets); (b) first slice only: the three fields in the template and schema, a computed level, the refusal below the level, `gov decisions answer` (M, about 200 lines), the page and the push by hand as today; (c) keep text and add only A-14, A-19 and A-28 (S each).
- **Recommendation:** (b), because the refusal is what makes the level a code decision and the page is a rendering of records that then exist; the push stays Claude Code's until a page exists.
- **Sources:** `GOLDEN-WORKFLOW.md` rule 8, W5; `decisions/command.py:36-52`; `T2-ESCALATION-RUBRIC.md`; `proposals/DECISIONS-BY-PAGE-SPEC.md`; audit 4 A-14, A-19, A-28; map rows 17 to 21.
- **Stops work:** no. It is a feature: a ticket needs the owner's approval.

### SQ-2. Does a chore land through `gov queue --direct`, or by a direct commit listed in the digest?
- **Found:** the draft's W12 says `gov queue --direct`; EMERGENCY-2 §4 and `CLAUDE.md` say a chore is "a direct commit, listed in the digest"; DEC-1238 (7) says "every landing through `gov queue`". The queue has no `--direct` (`queue/command.py:85-101`); `Class: C` is typed text (audit 4 §1.2 step 12; A-16).
- **Options:** (a) build `--direct` (impact-selected tests, no ticket, a notice when a `Class: C` commit changes `src/**` or `tests/**` beyond records; M, about 100 lines): every landing then goes through the queue; (b) keep the direct commit, add only the notice and the digest listing (S): a chore never runs a test through code; (c) both: the direct commit is allowed for records and docs only, and `--direct` carries the rest.
- **Recommendation:** (c): records and documents commit directly (no test could fail), anything that touches code goes through `--direct`; this keeps "the tests unchanged and green" a code check.
- **Sources:** `GOLDEN-WORKFLOW.md` W12; `EMERGENCY-2.md` §4.6; `CLAUDE.md` "three kinds of work"; audit 4 A-16, A-32; map row 70.
- **Stops work:** no; it blocks the ordering of A-16 in the plan.

No code runs the base today (`grep GREEN_ON_BASE src` is empty).

- **Recommendation:** (b): the point of red-on-base is that each KPI line has a test that can fail; a guard case that must stay green is a legitimate, marked, second kind.
- **Sources:** `GOLDEN-WORKFLOW.md` W9; audit 4 A-3, A-12; `fixes-015b` commit messages; `accept/runner.py:139`; map row 52.

### SQ-5. Where do schedules and git hooks live in an adopted repository?
- **Found:** W3 (retry), W4 (weekly), W16 and rule 4 all need schedules; Gov OS's are crontab lines the owner and CTO keep (live: the minute tick, the hourly backup, `@reboot`) and one untracked git hook; the kit installs no crontab and no hook (`template/` has `lefthook.yml.jinja`, not installed here). An adopted repository such as EXAMIN gets none of Gov OS's schedules except through the owner's shared crontab (the hourly backup covers EXAMIN by an explicit second line).
