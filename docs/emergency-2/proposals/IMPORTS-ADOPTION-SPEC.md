# Adoption of what a repository brings in

`docs/emergency-2/proposals/IMPORTS-ADOPTION-SPEC.md` · 2026-11-19 · written by the spec-writing method (problem, goals, KPIs with their failure lines, test data with its owner, open questions as packages). **Approved by the owner on 2026-11-19 (DEC-1222 (1): IM-0 yes, IM-1 (b), IM-2 (a), IM-5 (a)+(c); IM-3 and IM-4 changed by him); revised the same day to match.** Nothing here is built; no ticket file exists.

## Problem

A repository carries things it did not write: git submodules, copied libraries, another project's notes, a copied agent kit, datasets, models, tools and lock files. Adoption does not tell them from the repository's own work. Memory then reads them as the repository's own, so a question about the repository's behaviour can be answered from a library's README, a copied kit's rules or another project's decision, and nobody can ask which version of a dependency is used or why it is there.

**What the code does today** (read on `w2/integrate`, 2026-11-19; memory held no earlier design for this, so the answers come from the code):

- **Adoption sees no import as an import.** A1 lists every tracked file. A2 classes a file by the path map's namespace only and reads no content. A3 takes the adopter's proposal; the tool proposes none. The memory assessment (stage MA) flags vendored files by a folder-name list or a header phrase, and proposes a folder for vendored code that has none; it gives no class, no version, no origin and no licence.
- **A submodule leaves no trace.** Its entry is a commit, not a file; the assessment and the delete check skip it as "no file of this repository". No record, index or answer mentions it.
- **The record graph ignores the path map.** It reads every Markdown file of the commit that has an `id`, `type` and `status`. I checked on a scratch repository: a copied folder holding a decision `DEC-010` with `superseded_by: DEC-011` gave a second record `DEC-010` and a SUPERSEDES edge into the repository's own `DEC-010`. A copied kit's or a studied project's decision files can therefore demote the repository's own decisions, whatever the namespace says. The code graph also reads every tracked file, not the path map.
- **The path map already has what "place in memory" needs, as configuration:** a namespace's `embedding_policy` (embedded or not), its `lexical_policy` (indexed or not), its sensitivity, and the `retrieval_authority` block (ordered tiers by path or record, each step lifting or lowering a hit). Gov OS's own path map uses it by hand (`kernel-vendored`: vendored, not embedded, pinned in the tool registry). `memory_class` has only two values (governance, product), so a "research namespace" is a naming and policy choice, not a class. The path map's `research_corpus` switch is validated and read by nothing else.
- **People already do this by hand, in three forms, with no record of why or which version.** EXAMIN's path map holds `kernel` (not embedded), `archive-legacy` (not embedded, not indexed) and `research` ("reference only, never instructions", yet embedded and ranked like any own file: EXAMIN has no ranking block). Its tracked tree holds the Gov OS kit copied by `copier`, another governance kit under `archive/legacy-governance-kit/` (313 files), an `openspec/` folder that mixes a tool's schema with the repository's own specs, and `pyproject` dependencies; its 2.1 GB `product/data/` is not in git.
- **Real cost seen:** on the redis copy (W2-88's smoke run) the vendored `deps/` gave an over-limit chunk warning and a secret-rule hit (`deps/xxhash/xxhash.h`) that the owner has no way to mark as upstream's.
- **The Contract has no clause for imports.** Its neighbours: CAP-44.b/.e/.j (stages, legacy, native layout kept), CAP-01.c (research cannot silently become a decision; historical material cannot replace current), CAP-03 (sensitivity; secrets out of every index), CAP-45 (`gov update` keeps the overlay), CAP-25 (the tool registry, which is Gov OS's own tools, not an adopted repository's) and CAP-10 (memory judged end to end).

## Users and scenarios

- **The owner adopts a repository that vendors a library.** The adoption lists the library, says "use", records its version and licence. The library's text stays findable by keyword, in the last tier, labelled as an import; it is never embedded. He answers nothing unless the tool is unsure.
- **An engineer asks, "how do I call the parser?"** The vendored library's README is found and shown labelled as an import, so the agent can work with the library. Asked what the repository itself does, that README never answers.
- **An engineer asks, "what is the upload limit?"** The vendored library's README says 25 MB and "status: current"; the repository's own spec says 10 MB. The answer is 10 MB, cited from the own spec.
- **A CTO asks, "which commit of the parser is pinned, and why is it there?"** The answer comes from the import register: the pinned commit, who classed it and when, and the one-line reason.
- **The owner copies another project's repository next to his own to learn from it.** Its decisions carry identifiers like his. Asked "what did we decide about uploads?", memory answers from his decision. Asked "what did the other project do about uploads?", it finds the copy by keyword or by meaning, labelled as an import (study).
- **A copied kit's rules contradict the repository's** ("the engineer writes the tests"). Memory never offers them as the repository's rules, and the agent working in that folder is told they are not.
- **The owner changes his mind:** a study copy turns out to be worth taking from. He edits one register line; one run of the stage prints the path-map change; the copy's place in memory follows after a rebuild.
- **The EXAMIN CTO runs `gov update` to a new release.** The classes stay as they were.

## Goals

### What counts as "brought in"

Adoption reads git only (the tracked tree and history); it fetches nothing.

| Kind | Signs adoption reads | Proposed class | Pin it records |
|---|---|---|---|
| Submodule | a submodule entry in the tree and its address in the modules file | use | the pinned commit, the address, the branch if set |
| Subtree | the commit messages or trailers a subtree merge leaves (`git-subtree-dir`, `git-subtree-split`, "Squashed '<dir>/' content") | use | the upstream commit the merge names |
| Copied library | a folder in the assessment's vendored-folder list, or a folder with its own licence file and its own manifest naming another project, or a provenance note ("vendored from") or marker file | use | the version in its manifest, marker or changelog; else "unknown", and a question |
| Copied kit or kernel | agent instruction files or skills below the root (a second instruction file, a skills folder, role files) or another kit's manifest. The framework's own kit, named by its lock file, is the framework, not an import | study, always asked | the kit's own release marker, else "unknown" |
| Study repository | a folder with its own README and its own manifest, decisions or tests that no code of the repository imports or names | asked; held as study | its own head marker if any, else the date it was copied |
| Package dependencies | a manifest with its lock file (pip, uv, poetry, npm, yarn, pnpm, cargo, go, bundler, composer) | use | the lock file: direct dependencies and their pinned versions, dated. One line per manifest and lock pair, not one per package |
| Tool or binary | tracked executables or archives by their header; tool pin files (tool versions, runtime versions, toolchain, the build file's base images) | use | sha256 and size, or the pin file's line |
| Dataset or model | tracked data or model files by suffix, header, size or large-file pointer (the assessment's own lists) | use; product class where it is customer or runtime data | sha256, size, name |
| Declared | a line the owner writes by hand in the register; covers what git does not track (for example a data folder the repository ignores) | the line's | the line's |

**When unsure it asks, and never guesses silently.** Signs conflict when, for example, a folder named like vendored code was edited by many of the repository's own later commits, a folder is kit-shaped or study-shaped, or a copied folder has no clear origin. The stage then writes one decision package per item in A2's package form, with a one-line question ("`<path>` looks like `<sign>`: a dependency to use, something to assess and absorb, research to study, or our own? Recommended: `<class>`") and a recommendation. **While a question is open, the item is held as study**: findable by keyword (and by meaning under the size ceiling), labelled as an import, ranked below the repository's own sources, never a record. That is the least harmful guess in both directions (an own file wrongly held loses rank, not content; an import wrongly held cannot outrank the repository).

### The three classes (the owner's words, as DEC-1222 (1) changed them)

| Class | What it means | Path-map place | In memory | What the record holds |
|---|---|---|---|---|
| **use** | a dependency the repository runs on and does not own | text (library code, its docs): namespace `imports-use`: memory class governance, keyword index on, embedding off, sensitivity internal at least, tier `reference`. Non-text (datasets, models, binaries, lock files): namespace `imports-use-opaque`: keyword index off, embedding off (product class for customer or runtime data) | text found by keyword only, in the last tier, labelled as an import, so agents can find how to work with it; never embedded, never a record of the graph; non-text reached only through its register line | origin, kind, pin, licence note, who classed it and when |
| **absorb** | something to assess; the useful parts are taken into the repository's own code or spec | until parts are taken: as use. The taken parts are the repository's own files, in its own namespaces | the taken parts indexed as own with their origin noted; the rest as use | state `to-assess` or `taken`; for taken parts: own paths, origin, version, licence; what is left out |
| **study** | research to learn from, never the repository's decision | namespace `imports-study`: governance, keyword index on, embedding on **under the size ceiling**, sensitivity internal at least, tier `reference`. Over the ceiling: `imports-study-keyword` (embedding off) | found by keyword and by meaning, in the last tier, labelled as an import; never a record or an edge; never cited as the repository's decision | origin, date, class, reason, chunk count against the ceiling |

- **The size ceiling for embedding a study import: 2,000 chunks for one import and 5,000 for all study imports of a repository.** A chunk is counted as the assessment counts it (a file's size divided by 1,080 characters, rounded up), so the stage knows the figure without embedding anything. The basis: the assessment's lower bound for the embedder is 0.04 s a chunk, so 2,000 chunks cost at least 80 s and 5,000 at least 200 s; 5,000 chunks add about 16 % to Gov OS's own 31,373 vectors; and W2-81's legacy-documents repository (94,222 chunks) had not finished after 3,720 s, so an unbounded study copy is not affordable. An import over either ceiling goes whole to `imports-study-keyword`, the register says `over ceiling: <n> chunks`, and one question offers to raise the ceiling for it. The two figures are settings of the register, so a repository can change them. A3 refuses a study import over its ceiling in an embedded namespace.
- **The label the reader sees.** The store carries only a file's path, and the path map gives each path its namespace, which is the match the ranking already makes. Each item of a retrieval bundle (and each gap) from an import therefore carries a `label` computed at retrieval time from its namespace's name: `import:use` for a namespace beginning `imports-use`, `import:study` for one beginning `imports-study`; an own source carries none. No store change. The register line stays the place for origin and version. The brief's line telling the reader that a labelled item is reference and never the repository's decision or rule is kernel text, the CTO's call.
- **Ranking.** Both classes sit in one new last tier, `reference`, of the ranking block. The block's lift is additive, so "always below" is not guaranteed by the tier alone: the build sets the `reference` lift (or sorts that tier last) so that on the proving ground's decoy questions no import item precedes the own source that answers the same question, and the acceptance test is exactly that order (K5).
- **Absorb is assessed, not done, by adoption.** The tool judges nothing about usefulness (as AS judges "built or not" from code, commits and tests, never by a model). For an absorb import it writes a proposed assessment ticket in the kernel's ticket form, as MA writes its refactoring proposals (what is useful, what could be taken, the licence terms), and applies nothing. When that work lands, the register line gains the parts taken. Code the repository already took (a provenance note such as "adapted from X, MIT") stays the repository's own, indexed, and its origin, version and licence are recorded.
- **Licence is a note, never a gate.** The register copies the licence as the licence file states it (an SPDX id where the text is recognised, else "unrecognised, text at `<path>`"). A copyleft or unrecognised licence on an absorb candidate is named in the assessment ticket.
- **Sensitivity.** The secrets filter treats every class alike (CAP-03.e). Imports get sensitivity at least `internal`; the stage never lowers a namespace's sensitivity; the owner may raise it on the register line. Customer or runtime data stays product class and is never governance memory (CAP-03.b).

### The stage, the records, the confirmation

- **A new side stage, `IM` (imports),** modelled on AS (DEC-1200): after A2 and before A3; reads A1's inventory, A2's classes and git history; runs again at any time after A2, so an adoption recorded before it existed goes on and can add it. It writes only: `governance/adoption/IM-imports.md` (the stage record, standing on A2's record), the register `governance/project/imports.yaml`, one package per question, one proposed assessment ticket per absorb import, and the path-map lines it proposes. It edits no other file and moves, copies and deletes no import (CAP-44.j).
- **The register (`governance/project/imports.yaml`)** is in the project overlay, so `gov update` never writes over it (the update refuses and rolls back if the overlay changed). One line per import: `path`, `kind`, `class`, `state` (`proposed`, `confirmed`, `asked`), origin, pin, licence, who and when, optional `note`, optional raised `sensitivity`.
- **Who confirms.** A class the tool proposes from strong signs is confirmed at **A5**: the independent reviewer reads the IM record and the path map together, and the owner's A5 approval is the confirmation. A class the owner answers on a package is `confirmed` by his answer. No extra owner message per import.
- **The path map.** The stage proposes the lines that put each import in its class's namespace (`imports-use`, `imports-use-opaque`, `imports-study`, `imports-study-keyword`) and the one new last tier (`reference`) in the ranking block, and lists every path that would then fall in two namespaces. It edits no path map. **A3 refuses** a path map that holds a use import in an embedded namespace, a non-text use import in a keyword-indexed one, any use or study import outside the `reference` tier, or a study import over its ceiling in an embedded namespace, naming each path, and refuses to run before an IM record standing on A2 exists. The lite checks, as AS's: every import found has a class or a package; every package is one line with a recommendation.
- **The record graph skips imported Markdown.** A Markdown file of an import held as use or study, or of the left-over part of an absorb import, is searchable as text but is never a record, edge or supersession of the repository's graph.
- **After adoption.** A class changes by editing one register line and committing (a chore). One run of the stage prints the path-map change it needs. `gov check` names any disagreement between register and path map; `gov doctor` lists an import added later (a new submodule, a new vendored folder) with no register line. Both are notices that block nothing (EMERGENCY-2 3.2).
- **MA is unchanged** except that its vendored-code proposal names the import's class where the register has one.

### How memory behaves, judged end to end

- An import's text is found, and always shown labelled as an import and ranked below every own source on the same topic.
- A question about how to work with a dependency ("how do I call it") is answered from the use text, cited and labelled.
- A question about the repository's own behaviour, rules or decisions is never answered from a use or study text; the own source is found first and cited. Nothing labelled as an import is ever cited as the repository's decision.
- A question about a dependency's version, origin, licence or why it is there is answered from the register line, and cited to it.
- A question about a study source, put as such, finds it by keyword or meaning and says it is study.
- hit@k is a diagnostic only (EMERGENCY-2 5.2). The measure is W2-81's: the reader reads the whole ranked bundle and searches once more, answer and citation both right (DEC-1210 (1), DEC-1221 (1)).

## Non-goals

- No vulnerability scanning of dependencies, no advisory feed.
- No licence enforcement: a note, and a line in an absorb ticket.
- No network: no fetch of an upstream, no check for a newer version, even where a package says where it lives.
- No search by meaning of a use dependency (the owner's choice, DEC-1222 (1)); no embedding of a study import over its ceiling.
- No move, copy, rename or deletion of an import by adoption; no copying of code into the repository (CAP-44.j).
- No per-package register: one line per manifest and lock pair.
- No reading of untracked or ignored content; the owner declares such a line by hand.
- No model deciding what is useful in an absorb import.
- The framework's own kit and the tool registry (CAP-25) are not imports of the adopted repository.
- No change to the code graph's inputs in this feature (see Out of scope).
