## The answer in five lines

1. **Pinned and approved: yes, for ordinary tools.** The registry pins version and sha256, the install rule is written down and `gov doctor` catches drift. The registry has no MCP fields, no roles, no state and no scope or cost fields.
2. **Given to sessions: no.** `gov launch` starts every worker with `--strict-mcp-config` and refuses `--mcp-config`, so no worker can get any MCP server today. No `.mcp.json` exists in either repository.
3. **Kept from others: only for workers.** Leads (`gov launch lead`) start without `--strict-mcp-config`, so they get whatever MCP servers the owner's user scope and claude.ai account hold. Today that means the claude.ai connectors (Gmail, Google Drive, Google Calendar, Claude Docs). This audit session got them too.
4. **Adopted: barely.** `gov adopt` A8 moves an old MCP config's servers into `.rulesync/mcp.json`, but nothing ever generates them back. EXAMIN has no tool registry at all.
5. **REA: recorded by hand while this audit ran, and recorded well.** At `f7804392a` it had no registry line and no study folder. By the end of this audit the CTO had added two lines to the registry; they were committed in `e03dd938b` while I wrote this file:
   - `node-22.23.5`, because REA 6.10.1 needs node ^22.23.4;
   - `rea-agents` 6.10.1, with the tarball's sha256, installed locally in `~/gov-os-runs/study-startup-launchpad/tool` with `--ignore-scripts`; `rea setup` was not run.

   The study folder's `mcp.json` starts REA by absolute path. That is the right shape, but it is built by hand, and it reaches a session only if the session is started by hand: `gov launch` refuses `--mcp-config`. One new defect: `gov doctor` cannot find either new tool by name, so its tools check will turn red (row 5).

**Note on timing.** Every other row describes `f7804392a`. The two registry lines above, and the study folder, come from `e03dd938b` (committed while this audit was being written).

## Summary for the owner

Gov OS already pins and approves tools well: the registry holds version and hash, the CTO approves every install (G7) and `gov doctor` catches drift. But it cannot give an MCP tool to a session at all. `gov launch` deliberately starts every worker with no MCP servers and refuses to add any, and no repository declares one. The one leak runs the other way: leads start without that switch, so they and their helpers can use your claude.ai connectors (Gmail, Drive, Calendar), and a fix of one switch closes it. While this audit ran, the CTO recorded and installed REA by hand, and did it the right way: an exact version with its hash, installed only in the study's folder, REA's own `setup` (which rewrites agent configs) not run, and a pinned start line in the study's `mcp.json`. Those lines are committed (`e03dd938b`), and from that commit `gov doctor` reports red, because it cannot find tools installed outside the usual places; a small mapping fixes that. Until the launcher can hand REA to the study's sessions, those sessions are started by hand or call REA's command-line tool. The imports feature must add the rest:
- an MCP kind in the registry, with the roles that may use each tool;
- a launcher that gives each session exactly its role's tools and records them;
- doctor checks on the exact server command;
- a removed state;
- adoption that finds MCP servers in adopted repositories without switching them on;
- for code REA reconstructs, a record of which tool and version produced it and whether a commercial licence is held.

The spec needs one short MCP section first, because two of its lines say the opposite of your DEC-1228 (2).
