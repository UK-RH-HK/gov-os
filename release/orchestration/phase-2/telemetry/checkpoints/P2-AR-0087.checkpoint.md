## The mandatory deliverable: the floor is now bound to an authenticated transition, not the repository's public shape

OD-P2-08 §5 was deferred twice ("do not build a new hand-edit detector... reuse/adapt `cit::binding`"). This round
reverses that deferral rather than re-disclosing it, per the reviewer's explicit judgement.

**What the floor is bound to now (`runtime/src/paths.rs`):**

1. **Git lineage** (pre-existing, AR84-C3) — unchanged in kind and in code: `repository_lineage_id` still does a
   single `rev-list --max-parents=0 HEAD`, now via `constructed_env_command` (closing AR86-C8). An AR86-C2-specific
   toplevel check was built, closed the reproduction, and was REJECTED after the full suite found it broke an
   unrelated test for reasons not fully isolated within budget — see the "Update" section below. AR86-C2 is closed
   at the `FloorIdentity` layer instead (next item), independently verified to still work with no lineage-side
   change at all.
2. **`FloorIdentity`** (new) — a per-CHECKOUT anchor kept OUTSIDE the sealed document, in `.governance-state/
   adoption-floor-identity.json` (machine-local, BC-P2-31, the same `STATE_DIR`/`OS_STORES` pattern `claims`/
   `emergency-control` already use — not T2-sealed, for the same reason none of those are: OD-P2-08 §2 already
   concedes a full-OS-privilege adversary can forge a T2 seal, so sealing one more machine-local file would not
   raise that bar; what defeats the four reproductions is that the file lives OUTSIDE the document an ordinary
   `cp`/`git checkout <earlier> --` touches, not a second seal). Two fields:
   - `project_identity` — a fresh id (`uuid::Uuid::new_v4()`), minted the FIRST time `write_project_adoption_floor`
     is ever called for a checkout and never re-minted. Never derived from repository content, so a clone (shares
     lineage by construction) or a subdirectory (git used to report the same lineage for it) gets its OWN, different
     identity the moment ITS OWN onboarding runs — closes AR86-C1 and (the rejected toplevel check's replacement)
     AR86-C2, both on its own.
   - `max_known_sequence` — incremented by one on every write FROM THIS checkout. AR86-C3's reproduction restores an
     earlier document's own `floor_sequence` field, but not this file (which the restore never touches), so the
     restored document reads as stale against what this checkout already recorded. Ratchets forward only (never
     back), including on an ordinary `git pull` that brings in a teammate's already-committed, owner-authorised
     advance this checkout never itself executed.
   - A fresh checkout with no local ledger yet (a legitimate `git clone`, P2-ADJ-0002/NC3) ADOPTS the document's own
     claim as its baseline on first read rather than refusing it — there is nothing locally established yet to
     contradict it.
3. **Onboarding's own write has no CIT to bind to — handled by:** establishing the identity there directly (option
   named in the brief: "establish the identity at onboarding and bind subsequent changes to transitions"), and
   letting every LATER write reuse the SAME anchor. `reclassify_adoption_floor` (which DOES go through
   `cit propose -> simulate -> Human Gate -> approve -> execute`) writes through the exact same
   `write_project_adoption_floor`, so its ordering IS the record store's own CIT-id ordering
   (`RecordStore::next_id`) one level up — this file is the local, off-document ledger of that same ordering, not a
   competing one. I chose the local high-water-mark form over literally embedding a CIT id, because the review's own
   text offers both as equivalent ("or, equivalently... the id of the CIT/Human-Gate evidence... — closes C3") and
   the local form is cheaper (no `RecordStore::load` scan on every policy load, which is a hot path) while closing
   C1/C2 as well as C3 (a CIT-id embed alone would not, by itself, distinguish a clone/subdirectory's own identity).
4. **AR86-C6** (MEDIUM, disclosed-not-silent, but one of the reviewer's 7 probes so fixed alongside the rest):
   `FloorIdentity` also remembers the rule set of the last floor THIS checkout saw fully authenticated
   (`last_known_rules`). `policy::PolicySet::load`'s reconstruction fallback (AR82-C2/AR84-C1, fires once the
   authenticated record is already untrustworthy) now unions in any pattern from that remembered set the FRESH

## Property A — F1/F2 (`runtime/src/exec_resolve.rs`)

`is_trusted_dynamic_linker` no longer calls `std::fs::canonicalize` on the artefact's own `PT_INTERP` claim at all
(that resolves it in `gov`'s process, which is AR86-F1's exact defect). New `lexically_normalise` collapses `.`/`..`
arithmetically (clamping at an absolute path's own root, matching the kernel's own walk — needed for AR86-F3(c)'s
`/lib64/../../../<root>/evil-ld` shape to still land inside the project). `is_within_project_root` refuses ANY
`PT_INTERP` lying inside the project root outright (closes F2 — an unpinned project symlink — independently of what
it currently resolves to). Only the machine's OWN conventional loader candidates are ever canonicalised, to equate
two of THEM with each other (a distribution's own `/lib64` → `/usr/lib64` symlink) — never the artefact's claim.
