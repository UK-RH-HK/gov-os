# Output 4 — Trust-Chain Review

Method: for every link, ask **who can produce the reference value this link compares against**. A link is sound only if
no in-scope adversary (A1–A11 of `01-THREAT-MODEL.md`) can produce or select that value.

## 1. Link-by-link

| Link | Reference value | Produced by | Can an in-scope adversary produce or select it? | Verdict |
|---|---|---|---|---|
| L0 private keys | — | offline custodians | no (TA-4) | sound |
| L1 trust-root chain v1..N | public keys, roles, thresholds, revocation floor | root ceremony; **compiled** into the binary | no for the compiled chain. Newer links arrive in bundles or `governance/trust/root/`, are chain-verified, and can be **withheld or deleted** (A1/A2) | sound for authenticity; **freshness not durable** (RV-H2) |
| L2 DSSE signature | PAE(payloadType, payload) under a key of the payloadType's role | release role | no | sound for release statements; **role binding wrong for legacy identity** (RV-H4) |
| L3 statement payload | identity, full file map, tree/manifest/component/migration digests, compatibility, update impact | release signer | no | sound; the payload is complete (`schemas/release-statement.schema.json` has `additionalProperties:false` at every level). **E**: I reproduced the continuity claim for 4.1.2/4.1.3/4.1.4/4.1.5 (tree digest = published `release_hash`, manifest digest = `KERNEL_MANIFEST.json` hash, 113/117/119/121 files); the example payload regenerated byte-identically |

| L7 install transaction | L5 bytes | install_tx | writers outside install_tx can reach the same paths (CIT, adoption executor) | **incomplete** (RV-M1) |

## 2. Required properties from the review brief

| Property | Verdict | Basis |
|---|---|---|
| Trust ultimately originates outside attacker-controlled release contents | **holds** | compiled root; anchors never inside a kernel payload (`05` §2); bundle root links only extend a compiled chain |
| A release cannot manufacture its own trust anchors | **holds** | as above; statements never carry keys |
| Manifests, locks, metadata and caches cannot mutually self-attest | **holds for integrity/identity**; **fails for lifecycle freshness** | `manifest.json`, `KERNEL_MANIFEST.json`, lock and cache are ignored for trust. But *signed* lifecycle metadata (certification, revocation, root links) is accepted in whatever subset the adversary presents (RV-H2) |
| `framework.lock` records authenticated identity but never creates trust | **holds in RoT-1 semantics**; **leaks through older binaries** | `08` §1 and §3. Retaining the 1.1.0 field names lets 4.1.5 binaries keep minting `verified:true` from the lock (RV-M4) |
| Installed-kernel verification depends on authenticated release identity | **holds**, but authenticated ≠ current | a genuine 4.1.2 set verifies and serves as policy root (`06` §6, `11` Phase 4) with weaker floors (**E** R1) — RV-H1 |

## 3. Source authenticity versus installed-kernel integrity (review area 3)

The pack separates the two correctly. Source authenticity is `authenticate` V0–V14 before any trusted write.
Installed-kernel integrity is `kernel_trust` v2 comparing installed files with the signed map on every process. Neither
is used as a substitute for the other: a verified ingress is re-checked after commit, and a clean use-time check never
authenticates a source. V-H2 behaviour (substitution, `KERNEL_TAMPERED`, fingerprint-bound override) is preserved
(`04` §5, R-USE-4).

Two properties are missing from the vocabulary table (`00` §3). Both must be added before the chain is complete:

| Property | Question | Required mechanism |
|---|---|---|
| **Currency** | Is this authenticated material still acceptable as the policy root, or as a reason to relax a gate, for this binary now? | a T0 operational floor, strengthen-only floors against the embedded authenticated kernel, and freshness linkage between certification and revocation (`11-CORRECTION-DELTA.md` CD-1, CD-2) |
| **Byte binding** | Are the bytes being enforced the bytes that were verified? | an in-memory verified snapshot (CD-4) |

## 4. Git and transport independence (review area 9)

| Claim | Verdict |
|---|---|
| GitHub or private Git transport is not the trust root | **holds**. Transport is only a source adapter (R-NET-1..3). `build.rs` provenance from `git rev-parse` is removed (R-EMB-4). |
| A compromised repository or transport cannot create a valid certified release | **holds** without signing keys |
| A compromised repository or transport cannot change the *current* trust state | **does not hold**. It can deliver an older genuine release, a legacy kernel, or a stale certification, and strip revocations or root links (RV-H1, RV-H2). The pack does not claim this property explicitly, but its G4/TH-07/TH-08 coverage implies it. |
| An obtained valid release can be authenticated offline | **holds** (G5; RT-26) |
| Branch and tag names are not cryptographic identity | **holds**. `release_tag`/`release_branch` are signed provenance only; update gates bind `release_statement_digest` (R-UPD-5), replacing today's version-string gate lookup (`update.rs:109-116`). |

## 5. Certification separation (review area 11)

| Concept | Representation in RoT-1 | Distinct? |
|---|---|---|
| Release authenticity | release statement, release role | **yes** |
| Release-candidate status | `release.release_tag` string only (OP-4: no candidate role, no signed stage field) | **no**. Every signed candidate is a permanently valid production release unless revoked (RV-M5) |
| Independent verification acceptance | `verdict {path, digest}` inside the certification statement; the verifier holds no key and consumers never check the digest | **no**, only descriptive (RV-M5) |
| Final certification | certification statement, certification role, bound to the statement digest | **yes** |
| A correctly signed candidate does not automatically become certified | release statement has no certification field; the schema forbids additional properties | **holds** |
