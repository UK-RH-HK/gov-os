# Output 12 — Independent acceptance-test plan

This plan specifies **what** the independent verifier of 4.1.6 must prove. The verifier authors the harness
independently (held-out from the builder), as for WV-01…WV-06. Scenario IDs `RT-*` are proposals; the verifier may rename.

## 1. Rules for every scenario

1. Black-box through `gov --json` only; fresh consumer repositories; no builder helper code.
2. **No-trusted-write assertion**: hash `governance/` (including `trust/` and `framework.lock`) and `spec/` before and after
   each refused operation; they MUST be byte-identical (except a refusal ledger entry if the implementation records one,
   which must itself be declared in the report).
3. **Harm assertion** wherever the tamper removes a floor: a restricted MATERIAL record (as in V-H3 evidence) MUST remain
   excluded (`sensitivity:restricted`) and not retrievable.
4. **Typed refusal**: `ok: false`, the exact `error.code`, and `error.details.stage` where specified in `09` §4.
5. **Never-authenticated assertion**: after any attack, `gov kernel trust` MUST NOT report `authenticated: true` or
   `verified: true` for the attacked state, and doctor D030/D031 MUST be non-ok with CRITICAL severity where specified.
6. Key material for attacks (unknown keys, forged statements) is generated by the verifier. A second, independent
   Ed25519 implementation and an independent RFC 8785 implementation cross-check PAE bytes, signatures and canonical
   payloads.
7. Profiles: production-profile binary with an owner-signed 4.1.6 candidate statement for production semantics;
   test-profile binary with verifier-signed test statements for broad matrix coverage. Each scenario states which.
