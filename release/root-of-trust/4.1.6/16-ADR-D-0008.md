## Question

Four consecutive candidates were rejected for trust facts derived from artefacts controlled by the party seeking the
trust; V-H3 and probes E1–E5 show that install, update, reinstall, rollback, embedded-cache and Git ingress all mint
`verified: true` from self-consistency. Which root of trust governs every Governance OS release/kernel ingress?

## Options

| ID | Option |
|---|---|
| A | Bounded repair: verify sources against their shipped manifests and declared hashes (4.1.5 report §12) |
| B | Binary-embedded digest registry only |
| **C** | **RoT-1: DSSE-signed statements (Ed25519, RFC 8785 canonical payload) under trust-root metadata compiled into the binary; separate release, certification, revocation and profile roles; single authentication boundary; transactional install; use-time authentication of the installed kernel; lock as record** |
| D | Keyless signing with an identity provider and a transparency log as the root |
| E | Signed Git tags as the root |
| F | Full TUF deployment including online freshness roles |

**Recommended: C.** A is circular (E1, E2). B cannot extend trust after ship. D binds the root to a provider and to online
checks. E authenticates commits, not delivered bytes. F requires online roles incompatible with offline verification;
its rotation and threshold rules are adopted inside C.

## Consequences (abridged)

- Every ingress in `02-INGRESS-MAP.md` is rewired to `authenticate → authorise → install transaction`; install code
  accepts only `AuthenticatedRelease`.
- kernel_trust v2 authenticates installed content against `governance/trust/release.dsse.json` under T0 on every use;
  V-H2 behaviour is preserved.
- Certification and revocation become signed statements; `manifest.json` is descriptive only.
- `framework.lock` 2.0.0 records authenticated identity; it never creates trust.
- Development and test material cannot produce production-authenticated or certified state.
- Legacy 4.1.2–4.1.5 kernels are identified through a signed legacy-identity statement as `AUTHENTICATED_REJECTED`.
- Private GitHub or any host is transport only; verification is offline.
- Reference retrieval profiles use signed profile statements binding plugin, runtime and model digests without making any
  model constitutional.
