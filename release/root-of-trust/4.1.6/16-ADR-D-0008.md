## Question

Five consecutive rejections (4.1.3, 4.1.4, 4.1.5, RoT-1 revisions 1 and 2) share one class: a lower-trust input yielding
a current, higher-trust fact. Revision 2's instances were:
- registered floor keys taken as the constitution;
- repository or compiled knowledge taken as current state;
- a release key taken as binary authority;
- a sentinel read after acting taken as a boundary.

Which root of trust governs every Governance OS kernel, release and binary ingress and use?

**Recommended: C.**

- D is provider-bound and online.
- E authenticates commits, not bytes.
- F requires online roles. Its ideas are adopted inside C, with locally anchored or expiring freshness.

## Consequences (abridged)

- **Constitutional content.** Every file and leaf is classified by the root-signed Constitutional Surface; unknown content
  is denied; the release gate runs the coverage checker.
- **Freshness.** Trust state is shown as current only when anchored (pin, human confirmation or witness). Unanchored
  machines perform no trust ingress.
- **Binaries.** A binary is accepted only with two `release-artifact` signatures, an independent build attestation, a TSS
  reference and a Trust Base Manifest at or above the machine's high-water.
- **Trust decisions.** Local VTS confirmations only; repository gate records are requests.
- **Legacy binaries.** Pre-RoT binaries cannot write a RoT-1 project (executed against 4.1.2–4.1.5).
- **Consumers.** Legacy consumers update through one anchored, locally gated transaction that migrates the layout.
