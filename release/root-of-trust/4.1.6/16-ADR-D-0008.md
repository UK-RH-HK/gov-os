## Question

Four consecutive candidates were rejected for trust facts derived from artefacts controlled by the party seeking trust.
Revision 1 closed authenticity at ingress. The independent review showed four remaining gaps in the same class:
- authentic but historical kernels became current policy roots;
- signed lifecycle facts could be omitted or replayed stale;
- verified bytes were not the bytes enforced;
- a non-release key could confer kernel authenticity.

Which root of trust governs every Governance OS release/kernel ingress and use?

## Options

| ID | Option |
|---|---|
| A | Bounded repair: verify sources against their shipped manifests and declared hashes |
| B | Binary-embedded digest registry only |
| **C** | **RoT-1 revision 2**: purpose-separated DSSE statements under a compiled trust root; single authentication boundary; eligibility and non-downgradable floors from a root-signed Trust Policy lineage; monotonic trust state; verify-and-use install transaction and in-memory kernel snapshot; protected paths; trust-format boundary |
| D | Keyless signing bound to an identity provider and transparency log |
| E | Signed Git tags as the root |
| F | Full TUF with online timestamp and snapshot roles |

**Recommended: C.**
- A is circular (E1, E2).
- B cannot extend trust after ship.
- D binds the root to a provider and to online checks.
- E authenticates commits, not delivered bytes.
- F requires online roles, incompatible with offline verification. Its rotation, threshold, role-separation and snapshot
  ideas are adopted inside C, with “no relaxation without freshness” in place of the online timestamp.

## Rules

D-0007 rules (1)–(4) retained (rule 1 amended for eligibility), plus rules (5)–(18) (`15` §5), including the eight the
owner required:
- [O1] no authenticity from mutually consistent candidate files;
- [O2] authenticity ≠ eligibility;
- [O3] monotonic, freshness-protected trust state;
- [O4] verified bytes are the enforced bytes;
- [O5] domain-separated purposes and statement types;
- [O6] protected trust paths;
- [O7] incoming releases never set their own install authority;
- [O8] trust-format boundary for pre-RoT binaries.

## Consequences (abridged)

- Every ingress in `02` (I-01…I-47) goes through authenticate → eligibility → authorisation → install transaction. Every
  file mutation goes through GovernedFs.
- Kernel content is enforced only from a verified in-memory snapshot. Floors are the Trust Policy joined with the eligible
  kernel.
- Certification is visible only with an attestation, a certification statement and a trust-state reference. Under the
  recommended OP-3 mode A it never removes a gate.
- Historical 4.1.2–4.1.5 kernels are recognised but never eligible. Consumers on them are read-only until they update.
- `framework.lock` 2.0.0 is a record with sentinels that make pre-RoT binaries fail closed.
- Reference retrieval profiles use signed profile statements with host-side verification, without making any model
  constitutional.
